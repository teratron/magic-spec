# Status Command

**Version:** 1.0.0
**Status:** Stable
**Layer:** implementation
**Implements:** l1-session-continuity.md

## Overview

Concrete realization of the status briefing surface (SC-4/SC-5): a read-only `/magic.status` command with an engine body in `.magic/`, a user-facing wrapper in `workflows/`, and a generated skill wrapper in `skills/`. The command renders a resume briefing — position, progress, blockers, recent decisions, engine drift, and exactly one recommended next command.

## 1. Motivation

After a break the user must be able to run one command and learn: where the project stands, what was last done and decided, what blocks progress, and what single command to run next. Today this requires manually reading `STATE.md`, `TASKS.md`, `PLAN.md`, and `INDEX.md`. The status command is the engine's answer to "guide me back into the work".

## 2. Constraints & Assumptions

- **Strictly read-only**: no writes to `.design/`, `.magic/`, or any project file; no finalize invocation; no runtime version bump. (Authoring the command files is itself a one-time engine change governed by C14 during implementation.)
- The skill wrapper is generated by the engine-meta sync, never hand-edited (parity invariant of the skill projection).
- Must degrade gracefully: a missing `STATE.md` or a fresh project must produce a useful bootstrap briefing, never a crash.
- The briefing is cognitive composition by the agent from small files — no dedicated composer script in v1 (see §7).

## 5. Detailed Design

### 5.1 File Surface

**Project Structure:**

```plaintext
.magic/status.md                  (engine workflow body)
workflows/magic.status.md         (user-facing wrapper -> .magic/status.md)
skills/magic-status/SKILL.md      (generated projection of the wrapper)
```

### 5.2 Briefing Layout (output contract)

Rendered in this fixed order:

1. **Header** — workspace, `Status`, `Phase`, `Updated` (from `STATE.md`).
2. **Position** — current/last task ID and title, active spec (from `STATE.md` Current Position).
3. **Progress** — phase and overall progress bars, verbatim from `STATE.md` Progress.
4. **Blockers & Blocking Constraints** — both sections surfaced; constraints are mandatory reading before resuming work.
5. **Recent Decisions** — last 3 entries.
6. **Engine line** — local engine version vs. registry snapshot: `Engine: {version} (in sync)` or `Engine: {local} (snapshot {snap} — drift; /magic.analyze revalidates)`. Informational only.
7. **Next** — exactly one recommended command with a one-line rationale, in Decision Record format: `[DR] Next: {command} — {criterion}. (Override: any /magic.* command)`.

### 5.3 Resolution & Degraded States

- **Workspace resolution**: standard resolution chain (context load order, Priority 1-4). Optional argument `{workspace}` overrides. With multiple workspaces and no argument, render the resolved workspace and append a one-line `Other workspaces: {name} ({status}), ...` footer.
- **`STATE.md` missing** (fresh or partially initialized project): emit a bootstrap briefing — registry summary from `INDEX.md` (spec counts, statuses) plus the recommendation to run the planning workflow, whose auto-init provisions `STATE.md`. Never create files from the status command.
- **Paused session**: `Status: Paused` or a handoff file present → surface the resume line (handoff `next_action`, required reading) per the pause/handoff contract.
- **Unreadable artifacts**: each briefing section degrades independently — an unreadable source yields `{section}: unavailable ({reason})` instead of aborting the whole briefing.

### 5.4 Engine Upgrade Detection Interplay

The engine-upgrade detection rule (prompt to re-validate on version drift) is satisfied **inside** the status command by the informational engine line (§5.2 item 6): status never prompts and never auto-runs analysis — read-only purity (SC-4) takes precedence. The status command joins the analyze workflow on the detection rule's exemption list.

## 6. Implementation Notes

1. Author `.magic/status.md` (body) and `workflows/magic.status.md` (wrapper); run the engine-meta update once — version bump, checksum regeneration, and skill sync (`skills/magic-status/SKILL.md`) happen in that single pass (C14).
2. Verify generated skill parity (content matches wrapper, naming `magic-status`).
3. Add the status command to the upgrade-detection exemption list in the distributed agent rules; revalidate hardlinks after editing `rules/` (known breakage constraint C-001 in engine `STATE.md`).
4. Update the user-facing command table (README / distribution docs).

## 7. Drawbacks & Alternatives

- **Composer script** (`executor.js status` rendering the briefing) — rejected for v1: the briefing is a cognitive composition of small, well-structured files; a script would duplicate template knowledge and add maintenance surface. Revisit if briefing format drift is observed across agents.
- **Auto-resume** (status directly continuing the `Next Action`) — rejected: status is a guide, not an executor; resuming work is the user's explicit choice via the recommended command.
