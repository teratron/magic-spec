## [Unreleased]

### Fixed

- **`update-state` scalar-field patches no longer expand `$`-sequences from task titles** (engine v2.1.76 → v2.1.78): `updateState()`'s `fieldMap` loop patched each scalar `STATE.md` line (`**Phase:**`, `- **Task:**`, `- **Next Action:**`, …) with a string-form `content.replace(re, value)`. `re` has no capture groups, so the earlier replacement-string sweep (the entry family below, engine 2.1.57/2.1.62) cleared it — but that sweep only looked for `$`-*digit* backreferences and missed that `` $` ``, `$'`, and `$&` fire with **no capture group at all**. The patch value is not engine-controlled here: `nextAction` is `finalize.js`'s `synthesizeNextAction()` output, which embeds an arbitrary task **title**, and `--task` carries the raw title. A field agent (downstream project) hit it twice: a title containing bash ANSI-C quoting (`$'…'`) made `.replace()` expand `$'` to the **entire remainder of `STATE.md`** after the matched line, truncating `Next Action` mid-word and duplicating every section below it — a second, stale `## Progress` fence among them, which is why the report described "the Next Action **and** the Phase N line in `## Progress`" both broken from one call. Fixed to the function-form replacement the `## Progress` rewrite already uses (`replace(re, () => line)`), whose return value is spliced in verbatim with no re-scan. Spec amended: `l2-finalize-state-accuracy.md` 1.1.2 → 1.2.0 (new **§6.1** — retrospec per the §8 precedent; §6's "no other call site" claim retracted; one §11 regression bullet). New engine regression pins both the byte-for-byte field value and the structural invariants (no duplicated `##` section, balanced fence count); `dev/tests/engine.js` 68 → 69.

- **Consumer project name removed from shipped engine code** (engine v2.1.60 → v2.1.61): `utils.js`'s `parseFlags` JSDoc illustrated the flag-grammar bug using a consumer project's literal workspace name, carried over verbatim from the field report that produced the v2.1.54 fix. `.magic/scripts/` ships in the release archive, so a third-party project's identity was distributed to every consumer of the engine, in a comment where the name carries no meaning for the reader. Replaced with a neutral `docs`. Same containment family as RC-9 but a distinct direction: RC-9 forbids shipped files from referencing the *engine's own* SDD workspace, while this is a shipped file carrying a *consumer's* identity. Remaining occurrences are correct and stay: `dev/tests/engine.js` is L2 and never ships (fixture data), and the `CHANGELOG.md` entry records the actual field report, which is legitimate provenance.

- **SDD containment scan matches bare task IDs and prose phase designators; leaks now have a remediation owner** (engine v2.1.59 → v2.1.60): two compounding defects reported from a consumer project that had accumulated **121 leaks across 44 files with zero findings ever raised**, 16 of them inside a crate whose entire purpose is standalone extraction — where §6's stated harm is concrete, not theoretical. **(a) Notation bias.** The containment scan has no code: `phase-6.md` records it as "a cognitive grep procedure — no new executor script introduced (C2)", so the *prose statement of the match classes is the implementation*. Every audit surface (`rules/magic.md` §6, spec RC-2 and §4.2, `analyze.md` step 6) pinned task IDs to the bracketed literal `[T-XXXX]` and phase designators to the file form `phase-{n}`. Both are the SDD layer's own **internal** spellings — checklists bracket the ID, phase files are named `phase-N.md` — but a reference leaks precisely when it is *quoted out* of that layer: bare, in prose, inside a test name. Measured against this repository's own ledger: 11 of 74 generated task IDs carry two-digit phases (`T-18C01`, `T-22A01`) and so fall outside a fixed 4-character `XXXX`, and **all 74** fall outside a bracket-anchored match when referenced bare. The reporter's project had reached Phase 22, so nearly all of its IDs were in the missed class. Patterns are now notation-independent — `T-\d+[A-Z]\d+(\.\d+)?` bracketed *and* bare, `phase-\d+(\.md)?` plus prose `[Pp]hase[-\s]\d+` — with prose `Phase {n}` classified as the sole **contextual** class (many domains own the word), disambiguated by RC-3's self-containment test and reported in a separate sub-list for triage. **(b) No remediation owner.** RC-7 called ventilation "the cleanup path for legacy leaks" while ventilation is read-only by contract and the spec workflow's write scope is `.design/`-only — so the workflow that detects a leak is structurally forbidden from fixing it, and the promised cleanup path terminated at detection. The `SDD_REFERENCE_LEAK` finding now carries a stated path `→ /magic.task {ws}` (mirroring how `WIKI_STALE` states its sync path), scheduling a containment-cleanup task that `/magic.run` executes under the Coder role — the same role that owns the write-time gate. Ventilation stays read-only; only the routing was missing. Also hardened the write-time gate, which the report showed failing in practice (`transpiler.rs:1293`, `validator.rs:591` were introduced by the Coder role itself): both role cards now name the bare form explicitly, since the assigned task ID sits in working memory while writing and reads natural at the moment of typing. Specs amended: `l1-sdd-reference-containment.md` 1.1.0 → 1.2.0 (new **RC-2.1 Notation Independence**, new **RC-10 Remediation Owner**, RC-7 narrowed to detection-only, §4.1 gained a remediation surface row, §4.2 split into unconditional/contextual classes, §4.3 gained bare-form BAD examples), `l2-role-cards-execution.md` and `l2-role-cards-review.md` 1.1.0 → 1.2.0. Field report against engine 2.1.49.

- **No finalize branch can write a §5-reserved command into `Next Action`** (engine v2.1.58 → v2.1.59): the entry below fixed the `run` branch of `computeNextAction()` and deliberately left `task` returning `author new scope via /magic.spec {ws} (or /magic.status for a briefing)`, reasoning that finalize output is *inside* the task workflow where §5 permits the spec surface. That reasoning does not hold, and a second field report against v2.1.49 (re-verified against v2.1.58) surfaced the same violation through the surviving branch. The value is not workflow-scoped output — it is **persisted into `STATE.md`'s `Next Action`, which records no provenance, and `.magic/status.md` §39 replays it verbatim**. A `/magic.spec` written by a `task` finalize therefore resurfaces in the next `/magic.status` briefing, including one run right after `/magic.run` — precisely the seam §5 governs. The violation was simply laundered through live memory rather than emitted directly. Two further defects rode along: the string named *two* commands against §5's single-next-step contract, and `dev/tests/engine.js` **asserted** the violation in two places (`assert.match(next, /\/magic\.spec/)` in the unit test and in the e2e STATE.md check), so the bug was regression-pinned. Fix: the plan-complete branch is now uniform across every originating workflow (`Plan complete — run /magic.task {ws} to plan new scope`), and the §5 constraint is enforced as an invariant at the computation's **single exit** rather than per branch — a guard screens the synthesized value and degrades to the funnel with a warning, since branch-local enforcement is the demonstrated failure mode. Routing through the funnel is not circular: `/magic.task`'s Pre-flight raises the HALT that sanctions spec authoring, so new-scope work is still reachable, through the one sanctioned door. Specs amended: `l1-session-continuity.md` 1.2.0 → 1.3.0 (SC-2.1(b) reverted to workflow-agnostic; new **SC-2.2 Provenance-Free Field**), `l2-engine-finalization.md` 1.3.0 → 1.4.0, `l2-test-suite.md` 1.5.2 → 1.6.0. Regressions: the two violation-asserting tests inverted, plus a new sweep over the full *(workflow × plan state)* matrix asserting no branch emits `/magic.spec` or `/magic.analyze` and every branch emits exactly one command.

- **STATE.md progress recompute merges instead of clobbering** (engine v2.1.56 → v2.1.57): every finalize invocation passes `autoProgress: true` (SC-2 mandates fresh progress indicators — the field report's suggestion to make it opt-in was declined as it would violate that invariant), but `updateState()`'s recompute *wholesale-replaced* the `## Progress` fenced block, silently destroying any hand-authored narrative the operator had written there (reported: twice in one session). The recompute now distinguishes ownership inside the fence: counter lines (`Label: [done/total] …`, including template `{filled}/{total}` placeholders) are engine-owned and replaced; every other line is preserved below the fresh counters. The fence-matching regex also gained CRLF tolerance (same defect class as the phase-archiver fix above — on a CRLF checkout it previously failed to match and silently skipped the recompute). - **Phase archival no longer skips Done phases on CRLF checkouts** (engine v2.1.55 → v2.1.56): `phase-archiver.js`'s `parseFrontmatter()` anchored the frontmatter block on literal `\n` (`/^---\n…\n---/`), so a `phase-N.md` checked out with CRLF line endings (git `autocrlf` on Windows) never matched — the parser returned `{}`, `status` read as undefined, and a genuinely complete phase (`status: Done`, all items `[x]`) was silently excluded from `findArchiveCandidates()`. `archive-phases` reported "No completed phases to archive", and `finalize --workflow=run` appeared to skip archival — it *does* invoke `archiveCompletedPhases()` (the field report's secondary hypothesis of a missing wiring is disconfirmed); the empty candidate list was the same root cause downstream. Fixing only the block regex to `\r?\n` exposed a second layer: the per-line regex `/^(\w+):\s*(.+)$/` also fails on `phase: 16\r`, because `.` in JavaScript does not match `\r` (a line terminator) — so keys on CRLF lines vanished entirely rather than carrying a trailing `\r` into their values. Both layers are fixed (`\r?\n` block anchors + `split(/\r?\n/)` line iteration), matching the CRLF-tolerant pattern `check-prerequisites.js` already used; `graph-cache.js`'s `stripFrontmatter()` was audited and already handles CRLF. A new engine regression (7f) pins a CRLF fixture end-to-end: candidate detection plus clean `phase`/`name` values. Field report against v2.1.49 (Windows / Node 22).

In the same file, the Select step's branches gained an explicit evaluation order (*Stalled* → *Backlog-Only* → *Complete*): with `0 Todo, 0 In Progress, Done>0, Blocked>0` both *Stalled* and *Complete* were literally true (the *Complete* parenthetical even listed `Blocked` as a terminal status), so a rushing agent could fire Phase Completion — Retro L1 and Changelog L1 — on a phase that still had blocked work; `Blocked` now routes to *Stalled*. - **`--workspace <name>` no longer silently targets the default workspace** (engine v2.1.53 → v2.1.54): `executor.js` recognized only `--workspace=<name>`. The space-separated form left both tokens unconsumed, so `workspaceName` stayed null and every subcommand fell through to `workspace.json`'s `default` — writing `.design/main/CONTEXT.md` when a non-default workspace was requested, with no error and exit 0. Reported against `generate-context`, but the root cause sits in the executor's argument loop, and the blast radius is every subcommand routed through it. Six of the seven shipped call sites are `check-prerequisites` in the **Pre-flight gate** of `spec`/`task`/`run`/`rule`/`init`: on a non-default workspace, that gate validated the wrong directory and reported clean (verified: a workspace missing `INDEX.md` yielded `missing_required: []`). Worse, the `HALT: Unknown workspace name` guard was **unreachable** through the documented form — a typo'd workspace name silently redirected writes to the default instead of halting. Three sibling silent-fallbacks in the same parser are closed too: a bare `--workspace` at end of argv, an empty `--workspace=`, and `split('=')[1]` truncating `--workspace=a=b` down to `a` (which then passed the name guard). All four now HALT with a named reason. Argument parsing is unified in `utils.parseFlags()` — one grammar (`--flag=value` ≡ `--flag value`, valueless value-flags are errors, unknown tokens pass through untouched for proxying), shared by `executor.js`, `update-state.js`, and `finalize.js`. Unlike `SKIP_DIRS`, this constant *does* have one right answer (the GNU/POSIX convention is its oracle), so consolidation is safe rather than lossy — and the divergence between the three parsers is exactly what produced the field bug.

- **`update-state` no longer writes `STATE.md` into the registry root** (engine v2.1.53 → v2.1.54): a bare `--workspace` produced an empty value that fell through `parsed.workspace || MAGIC_DESIGN_DIR || '.design'` to `.design/`, so live session state landed at the global registry level (a variant of the WI-9 isolation break) while a `[update-state] Unknown argument` warning scrolled past on stdout, exit 0. The flag is now parsed under the shared grammar and fails closed. Note its `--workspace` takes a *directory* and is therefore deliberately NOT validated against `WORKSPACE_NAME_RE` — only `executor.js` and `finalize.js` (whose value becomes a path segment) apply the bare-name guard.

- **Workflow bodies prescribed an invocation the executor rejects** (engine v2.1.53 → v2.1.54): five call sites passed a *directory* to a flag that only accepts a bare workspace name — `update-state --workspace={active-workspace-dir}` in `run.md` (×3), `task.md`, and `pause.md` — which HALTs on `Invalid workspace name '.design/{ws}'` because `executor.js` already sets `MAGIC_DESIGN_DIR` for the child. All corrected to `--workspace={active-workspace}`, and the seven `--workspace {active-workspace}` space-form sites normalized to the equals form so the engine speaks one canonical dialect. A new test asserts no shipped workflow body passes a directory to the executor's `--workspace`; the field bug entered through a documentation line, not through user improvisation.

- **`generate-context` landmark roots are now truly always visible** (engine v2.1.52 → v2.1.53): the tree builder's "Ensure design directory is always visible" force-include only applied inside the workspace-scope filter and ran *after* the gitignore filter, so a scopeless run against a project that gitignores its design dir silently dropped the SDD root from the map. The design root (first segment of `MAGIC_DESIGN_DIR`) and `.magic` now bypass the ignore list, `.gitignore`, and the scope filter at depth 1 — they are the map's fixed landmarks; their inner entries still obey the normal filters.

- **Integrity check now detects removed engine files** (engine v2.1.51 → v2.1.52): `update-engine-meta --check` walked the files present on disk and asked the manifest about each one. That direction catches modifications and additions but is structurally blind to *removals* — a file listed in `.magic/.checksums` yet absent from disk was never visited, so the check reported `No changes detected` and exited 0. This is what would have let the CommonJS boundary above ship missing without any warning. The manifest is now traversed in the opposite direction as well: every entry with no corresponding file is reported by name, fails `--check` with an actionable message, and counts as an engine change in write mode (bump + regenerate). Exclusion rules mirror `generate-checksums.js` exactly (`history/`, `.checksums`, volatile caches), so there are no false positives.

- **`loadGitignore` unified across all four engine scanners** (engine v2.1.51 → v2.1.52): gitignore filtering existed in three divergent copies (`analyze-coverage.js`, `detect-communities.js`, `generate-context.js`) and was missing from a fourth (`extract-rationale.js`). All four now share `utils.loadGitignore()`. Consolidating exposed that no copy implemented gitignore's ordering rule, so the shared helper was rewritten to follow it: rules are evaluated in order and the **last match wins**, which is what makes the `.env*` + `!.env.example` idiom work; a pattern with a slash at the start or middle is root-anchored (`/dist`, `docs/build/`) while a slashless one matches at any depth; globs are path-aware (`*` and `?` stop at `/`, `**` crosses segments); an ignored directory is never rescued by a negation inside it. Behavior is pinned against real `git check-ignore` output. Previously `generate-context.js` honored only top-level slashless names, `detect-communities.js` dropped plain file patterns, and `analyze-coverage.js` silently never matched root-anchored `/dist`.

- **CommonJS scope boundary for engine scripts** (engine v2.1.49 → v2.1.50): added `.magic/scripts/package.json` declaring `{"type":"commonjs"}`. The engine installs *inside* a consumer repository, so its `.js` files inherited the module system from the consumer's root `package.json`. Downstream projects declaring `"type": "module"` made Node resolve every engine script as ESM, failing at the first `require()` with `ReferenceError: require is not defined in ES module scope` — a hard blocker for `/magic.*` and the pre-commit hook. The boundary file scopes `.magic/scripts/` (and `scripts/lib/`) back to CommonJS regardless of consumer configuration. A test now asserts the file exists, declares `commonjs`, and is **tracked by git** — the release archive is built by walking a fresh CI checkout, and `update-engine-meta --check` does not flag manifest entries whose file is absent, so an untracked boundary would vanish from the release silently.

- **`extract-rationale` now honors `.gitignore`** (engine v2.1.50 → v2.1.51): the rationale scanner walked the project with only a hardcoded `SKIP_DIRS` list and never read `.gitignore`, violating Invariant 7 (Gitignore Safety). Build artifacts leaked into the report — e.g. a `NOTE` marker harvested from rustdoc output under `target/doc/`, which `analyze-coverage` correctly excluded on the same tree. Gitignore filtering was duplicated across three scanners with divergent semantics and absent from a fourth; it is now a single shared `loadGitignore()` helper in `.magic/scripts/utils.js`, validated against real `git check-ignore` behavior (bare names at any depth, root-anchored `/dist`, nested path patterns, wildcard basenames). Ignored directories are pruned during the walk rather than filtered afterwards, so large build trees are never descended into.

- **Phase archival rewrites `PLAN.md` links** (engine v2.1.49 → v2.1.50): `archiveCompletedPhases()` rewrote `tasks/phase-N.md` references only in `TASKS.md`, leaving `PLAN.md` pointing at the moved file. Both indexes are now rewritten to `archives/tasks/phase-N.md`.

- **`build-spec-graph` coverage statistics and orphan detection** (engine v2.1.49 → v2.1.50): the coverage percentage divided a workspace-wide covered-file count by a single spec's scope size, mixing two coordinate systems and reporting figures above 100% (observed: 746.2%). Orphan detection compared scope entries to covered paths by string equality, so scope *directories* (`.magic/`, `docs/`) were reported as orphaned whenever their coverage was recorded against nested files. Both now compare by path prefix.

### Changed

- **`SKIP_DIRS` decomposed into a shared build-noise floor plus per-scanner domain excludes** (engine v2.1.52 → v2.1.53): the hardcoded skip list existed as five divergent copies — `detect-communities.js`, `extract-rationale.js`, `analyze-coverage.js`, `generate-context.js` (`ignoreList`), and the dev-side `benchmark.js`. The **build-noise half** of those lists (`node_modules`, `dist`, `build`, `target`, linter/test caches, virtualenvs) had drifted apart for no domain reason: `analyze-coverage` did not skip `build/` or `temp/`, `extract-rationale` did not skip `temp/` or `target/`, `detect-communities` missed `.pytest_cache`/`.ruff_cache`. The **domain half** legitimately differs per tool and must stay separate: `extract-rationale` excludes `.design`/`.magic`/agent-host dirs because SDD and engine internals are never user "shadow logic", while `detect-communities` and `analyze-coverage` scan those same dirs by design (they are the analysis subject). The tool-agnostic floor now lives once as frozen `utils.BUILD_NOISE_DIRS`; every scanner unions it with its own documented domain excludes. The floor remains a gitignore-independent safety net — unioned with `loadGitignore()`, never replaced by it. Behavior on this repository is unchanged (verified: identical coverage file lists and graph metrics before/after); projects that do not gitignore their build output now get the closed gaps uniformly. Test suite extended to 25: a parity guard asserts all five consumers spread the shared floor, closed-gap fixtures pin the new floor behavior, opposite-domain fixtures pin that `.design/` stays out of the rationale scan yet inside the community graph; the Invariant 7 extract-rationale fixture moved from `target/` to `generated/`, since `target` is now floor-skipped even without `.gitignore`.

- **Engine `commit-suggester` branch alignment** (engine v2.1.48 → v2.1.49): Fixed a bug in `buildChangelogBullet()` where the `'run'` branch would embed the task filename (e.g., `phase-N.md`) using `artifactId()`. Since tasks inside `run` often represent numbered phases, this leaked specific phase filenames into the root CHANGELOG, breaking symmetry with `'task'` and `'rule'` workflows. The `'run'` branch is now aligned with their generic style and does not embed the filename.

- **Engine `computeNextAction` logic fix** (engine v2.1.47 → v2.1.48): Fixed a bug where `finalize.js` would falsely report `"Plan complete"` on `task`/`run` workflows because it was only searching `TASKS.md` for task checkboxes (which actually live in `tasks/phase-N.md` files). It now uses a three-tier cascade lookup.

- **Bug Reporting Protocol added to agent rules**: Added Section 9 (`Bug Reporting Protocol (Engine Feedback)`) to `rules/magic.md` and updated the Section 8 Completion Protocol checklist. This instructs AI agents running the engine on user projects to output a standardized Markdown alert block (`MAGIC-SPEC ENGINE BUG REPORT`) when detecting engine-level errors or crashes, instead of attempting to self-repair the read-only engine files.

- **CHANGELOG trailing newline normalization** (engine v2.1.46 → v2.1.47): fixed the issue where updating the `CHANGELOG.md` file dynamically added an extra trailing newline on each run. The writer now normalizes the end-of-file formatting to a single trailing newline.

- **Cross-workflow consistency hardening** (engine v2.1.42 → v2.1.46): reconciled cross-file divergences across the engine workflows (surfaced by a composition audit), without changing intended runtime behavior (only mis-stated/contradictory branches were corrected):
