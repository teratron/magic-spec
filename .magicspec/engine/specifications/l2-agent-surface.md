# Agent Surface Architecture

**Version:** 2.0.1
**Status:** Stable
**Layer:** implementation
**Implements:** l1-engine-core.md

## Overview

Definition and structural governance of the adapter-facing surface for AI agents (`.agents/` directory). This specification covers what the repository keeps there: the link to the engine skill, the projections generated from it for the hosts this repository uses, and the maintenance workflows and skills.

## 1. Motivation

The `.agents/` directory provides capabilities tailored to AI pair programming adapters, and hosts reach it through links from their own folders (`.claude/`, `.codex/`, `.qwen/`). Without a dedicated specification in the `engine` workspace, changes to this directory are flagged as VIO-1 (Missing Coverage) during a Project Ventilation scan. This document resolves that gap and establishes clear architectural boundaries between the engine kernel and the agent extension layer.

## 2. Directory Structure & Components

The `.agents/` surface consists of three domains:

### 2.1 Workflows (`.agents/workflows/`)

- **Maintenance workflows:** `magicspec-dev:*.md` — repository-only commands (`/magicspec-dev:test`, `/magicspec-dev:sync`), authored here and tracked. They are not part of the shipped engine.
- **Command entries:** `magicspec/<command>.md`, generated by `init --host` for hosts whose command folder is a link to this one (a Claude Code command folder is). Each carries a marker, is regenerated, never hand-edited, and is ignored by git.
- **Rules:** must not reimplement core processing logic; entries point at the router and the body.

### 2.2 Skills (`.agents/skills/`)

- **The engine skill:** `magicspec`, a directory link to `skills/magicspec/` (§4, link table). It is the one place Codex and Qwen Code read the skill from, and Claude Code reaches it through `.claude/skills`.
- **Maintenance skills:** `magicspec-dev` (a link to `skills/magicspec-dev/`, the router and the four maintenance workflows; its command entries are written by `scripts/init/project-dev-skill.js`) and hand-crafted ones (`eval-prompts`, `reference-mining`). Each skill folder contains a `SKILL.md` (following the standard tool manifest layout). All are authored; nothing here is generated except the entries.

### 2.3 Rules (`.agents/rules/`)

`magicspec.md` — the agent-facing projection of the always-on rule: a byte copy of `skills/magicspec/AGENT-RULES.md`, written by `init --host`, marked, regenerated and ignored by git. It is the session-level convention a host agent inherits automatically, distinct from the global `RULES.md` project constitution (which governs spec authoring, not agent runtime posture). No content is authored directly under `.agents/rules/`.

## 3. Integration & Guardrails

| Constraint | Enforcement |
| --- | --- |
| **Kernel Separation** | Modifying the maintenance files in `.agents/` does **not** trigger engine metadata version bumps (C14) because they are extensions, not core logic. The projections are C14 **output**. |
| **VIO-1 Compliance** | `.agents/` is fully covered by this specification. Any new agent component MUST align with this defined structure. |
| **Universal Support** | Features in `.agents/` must avoid vendor lock-in (e.g., specific editor APIs) when possible, focusing on generic Markdown and shell invocations. |

## 4. Link Inventory & Validation Invariant

Some paths are not independently authored content — they share their content with a canonical one elsewhere in the repository.

**Hardlink group (shared inode) — one group:**

| # | Group | Anchor / canonical side | Linked side | Shape |
| --- | --- | --- | --- | --- |
| 1 | AGENTS family | `AGENTS.md` | `CLAUDE.md`, `GEMINI.md`, `CODEX.md`, `QWEN.md` | One anchor, N siblings sharing its inode |

Editing either side of a hardlink with an inode-replacing tool (most `write`/`edit` operations) silently delinks the pair: the edit always appears to succeed, and only the un-edited twin still shows the old content.

**Directory links (junction or symbolic link) — a closed table:**

| Link | Target |
| --- | --- |
| `.agents/skills/magicspec` | `skills/magicspec` |

A directory link leads to the real folder, so an edit through it is an edit of the real file and there is no delinking hazard. The table is checked by the real path of the link, never by content. `.claude/skills`, `.codex/*` and `.qwen/*` are links to `.agents/` made by the maintenance init script and are not part of the inventory.

**Invariant (mandatory)**: the hardlink group and every row of the link table MUST be covered by `scripts/validate-hardlinks.js`, and the `[C-001]` Blocking Constraint in every workspace's `STATE.md` MUST name the hardlink group by path pattern. A link added to this repository that is absent from both is a spec-compliance gap, not a deferrable follow-up.

**Explicitly excluded — generated files are not linked.** The rule copy and the command entries are generated from their sources and marked; their freshness is reported by the pre-flight (`PROJECTION_STALE`), not by the validator. Treating them as pairs would report false breaks on every regeneration.

**Provenance**: the earlier inventory listed three hardlink groups, the second and third being `rules/*.md` and `workflows/*.md` against their `.agents/` twins. It was authored after a production gap — `workflows/*.md` existed as a hardlinked pair with neither the validator nor `[C-001]` naming it, so an edit delinked it silently and the skill generator shipped a stale artifact while every integrity check reported success. The single-skill layout removes the pairs themselves, and the guard against the class of defect stays as the link table plus the AGENTS family.
