**Version:** 1.7.4
**Status:** Stable

## Overview

How this engine realizes the 4.0 document set: the tree of a workspace under `.magicspec/`, the scripts that check a set, compute a pack and record a build, the templates, what each workflow writes and reads, the migration of a 3.x workspace, and the order of delivery under the forward gate. The release that ships it is the major version 4.0.0 of the skill folder.

## 1. Motivation

The concept fixes the format; the engine has to write it, check it, read it and move existing projects onto it. The engine's present strengths — the router and one-stage pipeline, the input pass and intake survey, decision records and consequence forecasts, containment, finalization, the role gates, the graph, the diagnostics and feedback channel — carry over unchanged in what they decide; what changes is the files they write and read.

## 2. Constraints & Assumptions

- **Layer boundary.** The checker, the pack builder and the build recorder run in user projects, so they live in the skill folder's `scripts/` and require nothing from the maintenance folders; their fixtures and regression tests live in `tests/`.
- **C14.** Every change inside the skill folder runs `update-engine-meta`; the major bump to 4.0.0 is made once, by the release that ships the new tree as the default.
- **Both layouts during 4.x** (the forecast assumption of the concept, §2): a workspace whose `workspace.json` entry carries `"format": "4"` is read in the new layout; any other workspace is read as 3.x until migrated.
- **The lab's evidence is not shipped.** Only the format, its checks and their fixtures move into the engine; the runs and audits stay in the lab.
- **Assumption (forecast):** one stack per workspace in the first release, `stack/{stack}/` with a single entry; a second stack under the same neutral layer is the reuse path and comes later. Runner-up: several stacks from the start. Override: /magicspec spec amend l2-sdd-document-set-engine.md "several stacks per workspace in 4.0".
- **Assumption (forecast):** this engine's own workspace (`.magicspec/engine/`) migrates last, after the forward gate and after one consumer project has migrated, so the engine is never built from a format it has not yet proven. Runner-up: the engine workspace migrates first as the proving ground. Override: /magicspec spec amend l2-sdd-document-set-engine.md "migrate the engine workspace first".

## 4. Invariant Compliance (Layer 2 only)

| L1 Invariant | Implementation |
| --- | --- |
| I1 Computed pack | `run` hands a builder the output of `pack {task}` and nothing else; `pack` follows the order of concept §5.6 |
| I2 One address | the checker reports duplicate and unresolved addresses and names defined twice in a stack |
| I3 Pins behaviour only | `spec-critic` gains the lens "a sentence that pins a name or layout that changes no behaviour"; the change rules forbid pinning such names |
| I4 Decisions once | `run` writes `memory/decisions.md` at the moment of a build decision; `analyze` reports decisions whose `Moves to` is still open after the milestone |
| I5 Budget | the checker reports a pack over 10,000 tokens; `task` splits the task |
| I6 Exact seams | the checker reports produced names used before they are produced and consumed names without their defining unit |
| I7 Observable checks | the checker reports a task without `Done when … Observe:` and a milestone without `Observed by` |
| I8 Built code | `run` updates `memory/map.md` from Creates when a task is done (`mark-built`) |
| I9 Two layers | the checker reports neutral text that references a stack unit or uses the stack vocabulary; the neutral writing table ships as `templates/set/neutral-writing.md` (§5.3); `spec` runs the cross-stack review on a neutral layer before its first milestone, the table in the reviewer's hands |
| I10 Priority | the checker reports dependencies on lower priority and components traced at a lower priority than the work that requires them; `run` takes the ready task of highest priority |
| I11 Owners | the checker reports components and assets that no milestone closes and checkers named by rules that no milestone builds |
| I12 Recorded changes | `spec` on an existing set writes a change before touching any unit; `mark-built` records revisions; the checker reports stale units no task builds |
| I13 Containment | the containment rule's classes are the addresses of concept §5.2 and the set's paths; the existing scan points run unchanged |

## 5. Detailed Design

### 5.1 The workspace tree

```plaintext
.magicspec/
├── workspace.json           # workspaces, each with "format": "4" once migrated
├── INDEX.md                 # global aggregate: one row per workspace, engine snapshot
└── {workspace}/
    ├── product.md  rules.md  plan.md  changes.md
    ├── spec/{key}.md
    ├── stack/{stack}/profile.md  rules.md  deps.md
    ├── stack/{stack}/bind/{key}.md
    ├── stack/{stack}/tasks/M{n}.md
    ├── memory/state.md  decisions.md  map.md  goal.md
    ├── simulations/{area}.md
    └── archives/            # retrospectives and simulation reports, as in 3.x
```

| 3.x | 4.0 |
| --- | --- |
| `RULES.md` (global and per workspace) | `rules.md` of the workspace; the global constitution stays at `.magicspec/RULES.md` for conventions across workspaces |
| `{ws}/INDEX.md` registry with status per specification | the set itself; the checker's report replaces the registry's health columns |
| `specifications/l1-*.md` | `spec/{key}.md` (behaviour) and `product.md` (purpose, scope, decisions, needs) |
| `specifications/l2-*.md` | `stack/{stack}/bind/{key}.md`, `profile.md`, `deps.md` |
| `PLAN.md` phases | `plan.md` milestones |
| `TASKS.md`, `tasks/phase-{n}.md` | `stack/{stack}/tasks/M{n}.md` |
| `STATE.md` | `memory/state.md` |
| `STATE.md` `## Goal` (the record of `goal`) | `memory/goal.md` `[ADDED]` |
| `simulations/{area}.md` | the same folder, each scenario naming its milestone `[ADDED]` |
| Document History, amendment versions | `changes.md` and unit revisions |

### 5.2 Scripts

New executor subcommands, in `scripts/`:

- `check-docs [--workspace] [--budget N]` — the checker of concept §5.9; one finding per line on stdout and a summary line on stderr; exit 1 on findings. On a workspace that is not in the 4.0 format it prints one line and exits 0 (a 3.x workspace is not an error). A rule with no `From` line is no finding while `plan.md` defines no milestone, and one finding per rule once it defines one (concept §5.3: the plan stage writes `From`); a stack rule with `Realizes: —` is a convention only the stack has and needs no neutral rule. `[ADDED]` An HTML comment in a neutral file (`product.md`, `rules.md`, `plan.md`, `spec/`) is one finding per file; the reference scan skips text inside code spans, while the check of the component keys an `Observed by` names in backticks stays as it is. `[ADDED]` A component address that ends a sentence (`see hello.1.`) is a reference, to the checker and so to the pack and the graph; one followed by a full stop and more characters (a version, a file name) is not.
- `pack {task} [--workspace] [--include {file}]` — the pack of concept §5.6, written to `.magicspec/.cache/packs/{workspace}/{task}.md` (one folder per workspace, so two workspaces that use the same task address do not collide), a rebuildable cache that `clean-cache` removes; prints its size against the budget and says so when the computed units exceed it, because the checker, not the pack, is the gate. Its first line, before the task, states I13 for the task, in this text `[MODIFIED]`: `No address or path of these documents is written into anything this task creates; a component key is written only where the bindings use it as a name.` It is part of the pack file, not of the computed units, and counts toward no budget. After it comes the Tools section of the stack's `profile.md`, under the heading `# Tools of the stack`, before the task, likewise outside the computed units (concept §5.6: the runtime and its versions reach the builder). The component's preamble in the pack is its behaviour preamble and its binding's text before `## Units`, the Interface section included, as `check-docs` already computes it. **Done before this task** is read from the project: the files named in the `Creates` of the tasks the task is After, directly or not (concept §5.6), and, for a task of a milestone that revises or extends the component it builds, that component's interface files from its row of `memory/map.md`; `--include` adds a file as built, and a file that is not inside the project is refused. On a workspace that is not in the 4.0 format it prints one line and exits 0.
- `mark-built {milestone} [--workspace]` — records a done milestone: the `- Done: M{n} — {its Works after it}` line in `memory/state.md`, a map row for each component it builds that has none (from its tasks' Creates, test files left out of the interface files, and the task address an `(extends M{n}.T{k})` marker writes never taken for a file), Provides at each unit's revision, changes `placed` → `built`, `Was` lines of units built at their revision removed; a second run writes nothing, and a milestone not in `plan.md` is refused with nothing written.
- `check-log` — the order of change statuses in the history of `changes.md` (open before placed before built; `satisfied` takes no later status): every committed version, oldest first, and the file as it stands, read through git by argument list; one finding per change that went back, `changes.md: C{n} was {later} before {earlier}`; without a history it prints one line and exits 0.

Existing subcommands adapt: `check-prerequisites` on a 4.0 workspace reports the checker's findings in place of the registry findings (`SPEC_STATUS`, `ORPHANED_SPEC`, `SYNC_GAP`, header parity), which have no registry to read — one `DOC_SET` warning per finding, the registry, plan and ledger requirements dropped, a `doc_set` summary in its JSON; `resume-state` reads `memory/state.md` (`▶ Resume [{ws}]: Now {a} · Next {a} · Open {n}`, silent when neither `Now` nor `Open` holds something); `finalize` updates `memory/state.md` — its `Next` line is the next ready task (concept §5.4), the next step it names is the stage the set waits for (`plan` while a set with its stack layer has no milestone or a placed change none; `task` while a milestone has no tasks; `run` for a ready task or a milestone to observe; never `spec`, and no command when the stack layer is not written or every milestone is done), and it archives nothing and writes no `STATE.md` — and `changes.md` is written by the workflows only, never by `finalize`; `build-spec-graph` and `export-wiki` take units and addresses as nodes; `memory-query` indexes units by address; `analyze-coverage` measures requirements with an Accept that a task observes; `archive-phases` is retired for 4.0 workspaces (done milestones stay in `plan.md`, done task files stay as written).

**As built, the remaining subcommands** `[ADDED]`. `build-spec-graph` adds one node per unit (`unit:{workspace}:{address}`, with its address form and layer), a `contains` edge from the workspace and one `references` edge per pair a field or an address written in a unit resolves to; a set is left out of the 3.x coverage and orphan-file analyses, and the units are counted. `export-wiki` writes an article per document of a set, listing its units with the references each makes and receives. The artifact index reads a set's documents by their places (`product.md`, `spec/`, the stack's `profile.md`, `deps.md` and `bind/` → `spec`; the `rules.md` files → `rules`; `plan.md`, `changes.md` → `plan`; task files → `tasks`; `memory/` → `state`), so a query cites a unit by its heading, `{address} — {title}`. `analyze-coverage` prints, per requirement not covered, `{address}: unobserved` (an Accept, in no task's pack) or `{address}: unchecked` (no Accept), then `{c} of {n} requirements covered`, and compares `memory/map.md` with the code `[MODIFIED]`: after the requirement lines one line per map row whose path is not in the project, `map:{key}: {path} is missing`, and one per file of the workspace's scope that no row's path equals or contains, `{file}: no map row`, each group in path order, the summary then ending `, {m} map path(s) missing, {u} file(s) with no map row`. The files are those the 3.x walk takes (build noise and gitignored files out), without the state folder, the engine folder inside the project and the host folders; a row with no path names none; with no `memory/map.md` nothing is compared and the output keeps its form; `--json` gains a `map` key only when there is a map. A row whose path is `.` holds every file, and because `mark-built` writes a component's path as the common folder of its files, a file added under that folder is held by the row and not reported. `sync` reads no registry of a set and writes of the registry area only the set's row of the global registry, without a link to a registry (§5.5) `[MODIFIED]`, recomputes the `Next` line and reports each checker finding as a disagreement owned by `/magicspec spec`, `plan` or `task` as the bodies' sections assign them. `archive-phases`, `update-state` and `generate-context` print `[{tag}] {workspace} is a 4.0 workspace: {what takes its place}; nothing written.` and write nothing (`archive-phases --check` prints nothing), the goal flags of `update-state` excepted `[MODIFIED]`.

**As built, the goal record** `[ADDED]`. On a 4.0 workspace `update-state --goal-file {json}` writes `memory/goal.md`, exactly the section `lib/goal-block.js` renders, under the workspace's state lock, and `--goal-clear` removes it, each printing one line (`memory/goal.md written`, `removed`, or `absent; nothing removed`); a goal the schema refuses is refused as on 3.x with nothing written, and every other flag keeps the line above. `resume-state` reads the file beside `memory/state.md`: a goal is reported even with no state file, named after the `Now` line while a task is being built and otherwise followed by `/magicspec goal` as the step; the scope is spelled `M{n}` and `M{n}..M{m}`, the 3.x spelling unchanged.

### 5.3 Templates

New templates in `skills/magicspec/templates/set/` (the 3.x templates stay in `templates/`, and five of the names are theirs): `product.md`, `rules.md`, `plan.md` (milestone block), `spec.md` (component behaviour), `profile.md`, `stack-rules.md`, `deps.md`, `bind.md`, `tasks.md` (milestone tasks), `state.md`, `decisions.md`, `map.md`, `changes.md`; each holds the field lines of the concept verbatim and no example content. `[ADDED]` `memory/goal.md` has no template: the engine writes it, as `update-state` writes the goal section of a 3.x `STATE.md`, and no person or agent writes it by hand. The 3.x templates stay for 3.x workspaces until the line ends.

Beside them, `neutral-writing.md` holds the neutral writing table of concept §5.3 word for word, with the review sentence that follows it: guidance for whoever writes or reviews a neutral layer, no field lines, the one file of the folder that is not a template of a document. The templates carry the guidance lines of concept 1.1.0 in their comments and field lines: `rules.md` — `From` is added by the plan stage, and a rule written before the plan has none; `stack-rules.md` — `Realizes: {R addresses, or — for a convention only this stack has}`, such a rule listed in the Context of the tasks it governs; `profile.md` — the profile reaches no pack, so a convention a builder must follow is a stack rule; `plan.md` — `Closes: {component keys}`, `Needs: —` for none, a backlog with nothing waiting as `- none`; `tasks.md` — `Produces: —` for work no later task of the milestone uses, a test file a later task extends named as `{file} (extends M{n}.T{k})`, the exit status in the expected result of a command.

The guidance lines of concept 1.2.0, in the same way: `tasks.md` — a file a later task extends, source or test, written `` `{file}` (extends M{n}.T{k}) `` with the path alone in the code span, the task After the creating one directly or not; `Context` lists the stack rules that govern the task and a neutral rule only where no stack rule realizes it; `plan.md` — `Observed by` in neutral words, the profile's `observe` row saying how it runs; `profile.md` — the `observe` row maps each milestone's observation, the runtime and its test runner are in Tools with their versions, and no stack-only components is `- none`; `deps.md` — what is installed beside the runtime, a tool a task runs included, with version and checksum, or `- none`; `bind.md` — `Defines` lists bare names; `product.md` — a dependency marked `?` is one only an optional integration (a product item) needs; `spec.md` — a mark (`Assumption`, `Open`) is a list line after the unit's last field. `neutral-writing.md` gains the paragraph of the concept that repeats the review until a reading finds no earlier leak, without its closing section pointer, because a shipped file points to no section of a specification. The guidance lines of concept 1.3.0: `bind.md` — `Realizes: —` for a unit that realizes nothing, one visibility per unit (split a unit that would mix them), a binding unit built by one task, and the manifest pinned, path and content, by a unit of the component the first milestone closes; `plan.md` — the first milestone observed by running the product, Needs naming the milestones of direct dependencies only; `tasks.md` — one task per binding unit; `product.md` — what an external need is and what every runtime offers instead; `profile.md` — a vocabulary word matches as a whole word, in any letter case, and a component key never. The checker's vocabulary matching is already the one the concept states. `[ADDED]` The guidance of concept 1.5.0: every template's opening comment says that a document keeps none of the template's comments; `product.md` — what every stack provides by itself in place of the runtime's wording, and `- none` for no external need; `bind.md` — `Defines: —` for a unit that defines no name, and the manifest pinned by a unit of the component the product is run through; `tasks.md` — the task stage splits a binding unit the milestone needs in part or one too large, the first part keeping the address, and `Produces` names every consuming task, a unit with no name produced only to a task that extends its file; `spec.md` — a value shaped like an address written inside a code span; `neutral-writing.md` gains the table's row for the runtime. The checker already reads `- none` as an empty list (it takes libraries from `- X{n}` lines and stack-only components from table rows); a harness case pins it.

### 5.4 Workflows

| Command | On a 4.0 workspace |
| --- | --- |
| `spec` | **First version from an idea:** the input pass, the intake survey (E6) and the forecast as in 3.x, then `product.md`, `rules.md` and `spec/{key}.md`; the cross-stack review of the neutral layer; the stack layer when the stack is known. **An input after the first version:** the three steps of concept §5.8, the checker after every step. `amend` becomes a change. |
| `plan` | milestones from components, scope items and priorities; Needs justified; a change's milestone appended; the checker |
| `task` | the task file of the next milestone; each task's pack computed and within budget; a task whose pack holds an open unit is reported not ready |
| `run` | the next ready task of highest priority; the builder receives the pack; Done when observed; `memory/state.md`, `decisions.md` and, at a milestone's end, `mark-built` |
| `fix` | a reported defect becomes a change of kind `fix`: the code did not do what the units say, or the units were silent; the repair is its milestone and the regression check its Observe. A report the units and the code already answer is recorded `satisfied` and repairs nothing |
| `simulate` | scenarios from scope items and Accept lines; findings handed to `fix` |
| `goal` | unchanged in what it decides; its steps are the commands above, and its phase arguments name milestones (`goal M3`, `goal M3..M5`) |
| `analyze` | a 4.0 audit runs the checker and compares the map with the code; the reverse mode writes a set from existing code, the method the lab used |
| `migrate` | 3.x → 4.0 (§5.5) |
| `rule`, `status`, `graph`, `sync`, `help` | read and write the 4.0 files where they read and wrote the 3.x ones |

The roles keep their cards; `spec-critic` reviews units and changes, `planner` milestones and tasks, `coder` builds from a pack.

**As built, `spec`, `plan`, `task`, `run`** `[ADDED]`. Each of the four bodies carries one section, *On a 4.0 Workspace*, right before its finalization, taken when the workspace carries `"format": "4"`; the rest of the body applies unchanged, and the section names the 3.x mechanics that do not. One command runs one stage, so a change after the first version is handled across three: `spec` records it and edits its units (`placed`, with the checker reporting only what a missing milestone or task causes), `plan` appends its milestone and names it under `Built by`, `task` writes that milestone's tasks as soon as it exists, whether or not it is next, and `run` builds it, `mark-built` making it `built`; a clarification is `built` at once. `spec-critic` reviews in the `spec` section in place of the Post-Update Review. The cards of `spec-critic`, `planner` and `coder` end their operating protocol with their 4.0 line.

**As built, the remaining commands** `[ADDED]`. `goal`, `fix`, `simulate`, `status`, `rule`, `graph`, `sync` and `help` each carry the same section with the same first paragraph, before the finalization where the body has one (`fix`, `simulate`, `rule`) and otherwise before its completion checklist, named in the contents list where there is one; the text outside it is unchanged, except that `graph.md` and `status.md`, over 100 lines with the section, gained the contents list every long body carries. `goal`: milestone arguments, one criterion per milestone goal, the record in `memory/goal.md`, the next step read from the findings and then from the stage the finalization names, a one-task `run` under a task limit. `fix`: a change of kind `fix` recorded and placed by the steps of `spec` — an implementation defect names its component under `Affects`, no unit changing; `satisfied` when the units and the code answer the report; the reproduction in `Evidence`, observed by the task that builds the change. `simulate`: scenarios cite units by address and name their milestone on a `**Milestone:**` line. `status`: read-only through `check-docs` and `resume-state`, its next command a closed table in the finalization's order. `rule`: a workspace rule is a unit, `R{n}` or a stack-only `S{n}`, a change after the first version. `graph` applies per workspace by format, `sync` and `help` as their rows above state.

**As built, `analyze`** `[ADDED]`. The body carries the same section before its checklist. The audit (Modes B, C and D) runs the Mode C steps that read no registry as written, then `check-docs` and `analyze-coverage` with the owning stage of each finding, the containment scan with the classes of a 4.0 workspace, the set's rule units in place of a workspace `RULES.md` beside the global constitution, and `@role:project-auditor`; it writes no document of the set. The reverse mode (`analyze first-time` on a workspace with code and no `product.md`) writes the neutral layer, its review and the stack layer by `spec`'s steps from the code, the memory files from their templates, the milestones and every milestone's tasks, then replays: each task's `Observe` run against the existing code, done only when all hold, a failing one an `Open` line and never a change of the code, and each milestone recorded by `mark-built`. A workspace that holds `product.md` or no code is left to `spec`.

### 5.5 Migration

`/magicspec migrate --to 4` on a 3.x workspace: a dry run lists the mapping of every file (§5.1) and every specification whose content does not split into units without judgement; the new tree is written into the folder `next/` of the workspace by the analysis; one consent question; the apply step runs the checker on that tree `[MODIFIED]`. The new tree has a folder of its own, inside the one the registry names (WI-14), because `rules.md` and `RULES.md`, `plan.md` and `PLAN.md` are one file on a case-insensitive file system, the default on Windows and macOS. When the checker reports nothing, the step moves the 3.x files — every file and folder of the workspace but `archives/`, `simulations/` and `next/` — into `archives/3x/`, then the new tree out of `next/` into the workspace, removes the empty `next/`, and sets `"format": "4"` last. The 3.x archives under `archives/` and the scenarios of `simulations/` stay where they are; the dry run lists the scenarios whose `Verifies` names a 3.x specification. When a finding remains that the step cannot close, it leaves the workspace on 3.x with both trees in place — `next/` beside the 3.x files — and prints the findings, and a second run resumes from `next/`. No 3.x reader reads `next/`.

**Resuming a move** `[ADDED]`. Each move is read back from the files, so an interrupted run continues where they stand, and the format is set only once no 3.x file is left outside `archives/3x/`. While a workspace is not in the 4.0 format and its `archives/3x/` holds files, the move is in flight: every command but `migrate --to 4` stops on that workspace and names `/magicspec migrate --to 4` as the one way forward, as a command on an unmigrated project names `/magicspec migrate` ([l1-command-surface.md](l1-command-surface.md) CS-8), so nothing reads a half-moved tree ([l1-skill-packaging.md](l1-skill-packaging.md) SP-10).

The split of an existing specification into product items, requirements and binding units is done by the `analyze` reverse mode against the code, writing into `next/`, not by text transformation; a requirement that has no Accept check becomes an `Open:` line. The command's argument and consent are [l1-command-surface.md](l1-command-surface.md) CS-6 `[ADDED]`.

**As built, the move** `[ADDED]`. `migrate --to 4` is `scripts/lib/migrate-to-4.js`, called by `migrate.js`; another value of `--to`, and `--host` beside it, are refused. One table of places is read by the dry run and by the apply step. The dry run prints each file of the workspace with its place, one line per specification to split, one per scenario whose `Verifies` names a specification, and the state of `next/` (absent, the findings, clean); when a move is under way it says so, and when the set is partly moved up it prints that one line. The workflow runs the dry run; for a set that is not ready it creates `next/`, which marks the move for the analysis, and ends naming `/magicspec analyze first-time`, whose reverse mode writes into it and checks it by that dry run (`check-docs` reads a registered 4.0 workspace only), running no `pack`, `analyze-coverage`, wiki refresh or `mark-built` there; for a clean one it asks the question, applies, and then records the built milestones with `mark-built`. The apply step refuses an absent or failing `next/` and a file that would land on another, changing nothing; it moves the 3.x entries to `archives/3x/` (merging a folder that is already there), then the tree up with `product.md` first, removes `next/` and sets the format, keeping the indentation and line ends of `workspace.json`. Where a move stands is read from the files: `product.md` in the workspace, gone from `next/`, with no 3.x entry left at the root, means the set is on its way up, and a partial `next/` is then not checked again. The report's revert hint, before a commit, restores the workspace folder, `workspace.json` and the global registry and then deletes the workspace's `archives/3x/`: its copies stay untracked, and while a file is there and no format is set the move reads as unfinished `[MODIFIED]`.

The stop is the executor's, beside the stop of an unmigrated project: every command on the resolved workspace but `migrate`, `resolve-workspace` (the move chooses its workspace by it) and `remove` and `install-hooks` (they read no workspace) exits 1 with `HALT: The move of {workspace} to 4.0 was started and not finished.` and the command that finishes it, naming the workspace in it when it is not the default.
