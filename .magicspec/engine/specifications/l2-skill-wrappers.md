# L2 Specification: Router Skill & Host Surfaces

**Version:** 3.0.0
**Status:** Stable
**Layer:** implementation
**Implements:** l1-engine-core.md

## Overview

The router skill through which every host reaches the engine: the router's contract (grammar, command table, dispatch), the frontmatter limits a host enforces on it, and the projections generated from the engine folder for each host — the rule copy, the pointer block and the skill link. Since 3.0.0 the router is the only command surface: no host receives a per-command entry.

## 1. Motivation

To give disparate AI agents (Claude Code, Codex, Qwen Code and others) one native entry to the engine: a single skill, invoked as one command, whose router sends each command name it receives to its workflow body, so that no host needs a second copy of the logic or a per-command entry. `[MODIFIED]`

## 2. Architecture

### 2.1. Surfaces

| Surface | Source | Generated by | Where it works |
| --- | --- | --- | --- |
| Router `skills/magicspec/SKILL.md` | authored once | nobody | every host that loads the skill |
| Rule copy, pointer block, skill link `[MODIFIED]` | `AGENT-RULES.md` | `init --host=<name>` ([l2-skill-distribution.md](l2-skill-distribution.md) §5.1-§5.3) | per host |
| Router `skills/magicspec-dev/SKILL.md` | authored once | nobody (entries: `scripts/init/project-dev-skill.js`) | the developer repository only |

Every surface resolves to a file in `workflows/` (SP-5); the shipped engine has no generated wrapper of its own, and since 3.0.0 of this specification no host receives a per-command entry either (the owner's decision of 2026-10-30). The maintenance router keeps its own entries in the engine's repository; they never reach a user.

### 2.2. The Router

`SKILL.md` carries the frontmatter (`name: magicspec`, one `description`) and a body that states the grammar `/magicspec <command> [argument]` (`$magicspec <command>` on a host that invokes skills with a dollar sign; the colon spelling typed as text is read, never printed), the command table (one row per command: name, group, one-line summary, argument and what happens when it is missing, body path), the dispatch steps — the interactive help for a bare or unknown invocation and the argument form for a missing required argument ([l1-command-surface.md](l1-command-surface.md) CS-3, CS-9, CS-10) — and the pointer to the always-on rule. The table is the one list the help is rendered from. `[MODIFIED]`

**Argument hint.** `[ADDED]` On a host that completes skill arguments, the router's frontmatter declares `argument-hint: <command> [argument]` (Claude Code documents the field: a hint shown during completion, which changes nothing in how arguments are passed; read 2026-10-30). It is not description-like text, so rule 4 of §2.3 does not apply to it. <!-- TBD: confirm that Codex and Qwen Code accept an unknown frontmatter field without rejecting the skill; otherwise the hint is omitted for them. -->

### 2.3. Frontmatter Contract `[ADDED]`

A host reads two fields of the router before anything else in it: `name` and `description`. The validity limits below belong to the target skill format — a router that breaks one is rejected or silently ignored by the host. The Selection Signal below is the form `description` needs for a host to choose the skill at all.

**Validity limits (hard):**

| Field | Requirement |
| --- | --- |
| `name` | 1–64 characters; lowercase letters, digits and hyphens only; no `<` or `>` character; no word the target skill format reserves (at present its vendor's and its model family's own names); equal to the folder name (`magicspec`). |
| `description` | Present and not blank; at most 1,024 characters; no `<` or `>` character; valid YAML as a plain scalar (a colon followed by a space is not allowed). |

**Selection Signal (form).** While a host chooses among every skill installed in a project, `description` is the only text it holds about this skill — the body is loaded after the choice. It therefore says what the engine does and when to use it:

1. **Two parts, in order.** The first sentence states what the engine does, leading with its primary use, so a host that truncates a long skill listing keeps the part that matters most. A later sentence begins with `Use when` and names the situations that call for it, in the words a user would use for them.
2. **Discriminating.** The `Use when` sentence names the artifact or state the commands act on — the plan, a task list, the registry, a rule file, the session position. A bare verb (run, apply, continue, check, start) is never its only cue.
3. **Third person.** The description declares what the skill does; it never addresses the reader or speaks as the agent: none of the whole words `I`, `we`, `my`, `you` and `your` appears in it.
4. **One field.** The `Use when` sentence lives inside `description`; there is no second description-like field.
5. **Names the commands.** One description serves every command, so it lists them by name; a host selects the skill, and the router selects the command. `[MODIFIED]`
6. **One authored source.** The text is the router's own frontmatter. No script composes, trims or completes it.

Per-command selection lines live in the router body, where a host reads them after choosing the skill. The full list of natural-language trigger phrases stays in each workflow body.

**Reading.** The checks read the frontmatter as a host would: a quoted or folded multi-line value is measured as its text, and a frontmatter block that does not parse counts as a missing description.

## 3. Synchronization

### 3.1. Version and Projections

The integrity manifest covers the whole folder ([l2-skill-layout.md](l2-skill-layout.md) §5.4), so a change to a body, the router or the rule source is a version event on its own, and the earlier asymmetry — a `workflows/` edit invisible to the manifest — no longer exists. After a bump, the C14 write branch calls `refreshProjections`: it rewrites the projections that already exist and have fallen behind their source, removes every command entry it finds (all are retired), and creates nothing; `[MODIFIED]` a file at a projection path with no marker is never touched. A file reached through two hosts' links is one projection. In a user installation the write branch refuses before anything is touched. `update-engine-meta --check` never writes.

### 3.2. Staleness

A projection that differs from its source is reported by the pre-flight as `PROJECTION_STALE` with the remedy `init --host=<name>` ([l2-skill-distribution.md](l2-skill-distribution.md) §5.1). The pre-flight changes nothing.

### 3.3. Generation-Time Validation `[ADDED]`

The checks of §2.3 run in the harness over both routers (`scripts/skill-frontmatter.js`, `checkProjection`, is the one implementation) and `init --host` reads the router and the rule source before it writes anything: an unreadable router, or an unknown host name, stops the run with nothing written. A router that breaks a rule fails the harness, on the contract a generator once enforced by refusal:

| Rule violated | What it protects | Outcome |
| --- | --- | --- |
| A validity limit (the §2.3 table) | The host rejects the skill or silently ignores it, so the output is invalid whatever its other merits. | **Refused** |
| A Selection Signal rule decidable mechanically: no `Use when` sentence, a first- or second-person word, a synthesized description | The skill works but is chosen less reliably; the owner decided that such a skill is refused all the same. | **Refused** |

A refusal writes nothing and leaves an existing valid file as it was; it names the source, the field and the limit or rule; it is recorded as an `error` finding (DG-2) and the run ends non-zero while every other file is still checked. A dry run (`MAGIC_DRY_RUN`) checks and reports exactly as a real run would, but writes nothing. A skill that carries no generated-file marker is outside the contract.

**Judgment.** Rule 2 (discriminating) and the primary-use lead of rule 1 are judgments no script can make: they are reviewed at authoring — the prompt-engineer's scope-ambiguity dimension — and probed by the cognitive selection cases of the suite.

## 4. Integration & Deployment

### 4.1. Development Workspace

`/magicspec-dev:init` creates the link from `.agents/skills/magicspec` to `skills/magicspec` and runs `init --host` for the repository's hosts; the agent folders reach `.agents/` through links ([l2-skill-layout.md](l2-skill-layout.md) §5.6).

### 4.2. End-User Installation

The release archive carries `skills/magicspec/`; the user places it in a host skills folder and runs `init --host` ([l2-skill-distribution.md](l2-skill-distribution.md) §5.3).

## 5. Invariants

- **Parity**: the router's command table and the files of `workflows/` name the same commands ([l2-workflow-wrappers.md](l2-workflow-wrappers.md) §6).
- **Marker**: every generated file carries a marker; `remove` and the staleness check find it without a separate record (SP-6).
- **Generated is read-only**: a projection is regenerated, never hand-edited; a file with no marker belongs to the project and is never overwritten.
- **Frontmatter Validity** (§2.3): the router's `name` and `description` meet every validity limit; the harness holds the shipped router to it.
- **Selection Signal** (§2.3): the router's `description` states what the engine does and, in a `Use when` sentence, when to use it — third person, discriminating, one field, authored only in the router, naming the commands. The mechanical rules are held by the harness; discrimination and the primary-use lead are judged at review and probed by the selection cases.
