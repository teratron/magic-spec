# Engine Automation Specification

**Version:** 1.24.1
**Status:** Stable
**Layer:** implementation
**Implements:** l1-engine-core.md

## Overview

Implementation details of the Magic SDD automation scripts.

## Motivation

Automate repetitive tasks like checksum generation, versioning, and environment resolution.

## Components

- **executor.js**: Cross-platform wrapper for JS and Shell/PowerShell scripts. Resolves the project root and the workspace, and runs the script from the root (§Project Location).
- **check-prerequisites.js**: Validates engine integrity and project state.
- **generate-checksums.js**: Maintains `skills/magicspec/.checksums`. Honors `.gitignore` during the file walk (Invariant 7 parity).
- **generate-context.js**: Regenerates `CONTEXT.md` from current project state.
- **init.js**: Scripted setup of the `.magicspec/` directory.
- **install-hooks.js**: Installs the git pre-commit hook that runs the integrity check (§Git Hook Lifecycle).
- **analyze-coverage.js**: Confidence Taxonomy engine — classifies project files by spec coverage confidence (EXTRACTED/INFERRED/AMBIGUOUS/UNCOVERED, plus EXEMPT for SDD bookkeeping files — see §Coverage Denominator Scope) using Canonical References from specifications.
- **extract-rationale.js**: Rationale Extraction engine — scans source code for design rationale markers (NOTE/WHY/HACK/etc.) and identifies Shadow Logic (uncovered design decisions).
- **detect-communities.js**: Workspace boundary analysis — builds the dependency graph, detects communities, and scores Jaccard alignment against `workspace.json`. Honors `.gitignore` during the file walk (Invariant 7 parity).
- **check-bloat.js**: Context-economy advisory — flags oversized specs and task phases against configurable thresholds (see §Bloat Advisory Configuration).

## Logical Flows

### Zero-Prompt Resolution

1. Check `MAGIC_WORKSPACE` env.
2. Check `--workspace` flag.
3. Use `default` from `.magicspec/workspace.json`.
4. Fallback to `.magicspec/`.

**What a child script actually receives.** `executor.js` resolves the workspace by the order above, then forwards only the *result* to the child process — as `MAGIC_DESIGN_DIR` (plus `MAGIC_WORKSPACE_SCOPE` when the resolved workspace declares a `scope`) in the child's environment, never as a `--workspace` argument: `parseFlags` strips `--workspace` from the argument list before it is passed through (`executor.js`, `passThroughArgs`). A script therefore cannot distinguish "the caller passed `--workspace`" from "no flag was given and step 3 or step 4 supplied the default" — both arrive as the identical evidence, one `MAGIC_DESIGN_DIR` value. A script needing that distinction (an "every workspace" scope, say) needs its own explicit flag; it cannot infer scope from the resolution order. An ambient `MAGIC_WORKSPACE` set in the caller's own shell is not consumed by this forwarding — `childEnv` is built by spreading `process.env` first, so it reaches the child process unchanged alongside the two variables above, exactly as it reached `executor.js` itself.

### Project Location — the Engine Acts on the Project It Is Run In

An engine command acts on one project however deep the caller stands and wherever the engine folder lies (`l1-skill-packaging.md` SP-2, SP-8). Two locations are kept apart and each has one definition, in `utils.js`:

- **The project root** — `resolveProjectRoot()`, the first of: the `--root` argument, the `MAGIC_ROOT` environment variable, the nearest ancestor of the working directory that holds the state folder, the nearest ancestor that holds a `.git` entry, the working directory itself. An explicit root that is not a directory stops the command with one message naming its source. Ancestors are walked on the path the operating system reports for the working directory; links are not resolved, so a project reached through a junction keeps its own ancestors.
- **The engine folder** — `engineRoot()`, the folder that holds `.version`, `templates/` and `scripts/`, found from the library's own file. Templates, role cards and the version are read through it. It is the real location, which for a linked or cached installation lies outside the project.
- **The state folder name** — `STATE_DIR_NAME`, with `statePath(root, …)` to build a path inside it. No other script spells the name in code; comments may.
- **The graph artifacts** — `graphPaths(stateFolder)`: the cache, the wiki, the page and the two snapshots under `graph/`, and the five earlier locations; `retireLegacyGraph` removes or moves the latter once a writer has succeeded (`l2-spec-graph-memory.md` §4.6).

**The executor** consumes `--root` as it consumes `--workspace`, resolves the root once, exports it to the child as `MAGIC_ROOT` beside `MAGIC_DESIGN_DIR`, reads `workspace.json` from it and runs the child with the root as its working directory, so a path typed on the command line is relative to the project. **A script** resolves the root itself, so a direct invocation behaves the same: scripts that form their paths from a root variable call the resolver for it; scripts whose paths are all root-relative (`check-prerequisites`, `generate-context`, `extract-rationale`, and `update-state` when run as a command) change into the resolved root before they start. The diagnostics library resolves its sink when the module loads and falls back to the working directory rather than throw, because a finding that cannot be recorded must not become a second failure. A module loaded in-process by a test is loaded with `MAGIC_ROOT` set to its fixture.

The maintenance fallbacks (`../../dev/…` in `update-engine-meta`) and the dev-repository probe keep their present form until the maintenance layout moves.

### Engine Meta Update Flow (`update-engine-meta`)

1. Scan `skills/magicspec/` against `.checksums`: a modified, added or missing engine file is drift (a checksum delta). The manifest covers the whole folder, so an edit to any body, role, template, script or the rule source is drift; when nothing under `skills/magicspec/` changed, nothing is owed and nothing runs.
2. Increment patch version in `skills/magicspec/.version` (write mode; refused in a user installation — see below).
3. Refresh the host projections that exist — the rule copy, the command entries, the pointer block — from the folder just changed (`refreshProjections` in `lib/hosts.js`): a stale one is rewritten, an entry whose command left the router is removed, a host with no projection gets none, and a file with no marker is never touched.
4. Developer repository only: refresh the `**Engine Version:**` snapshot in `.magicspec/INDEX.md` (`scripts/sync-engine-snapshot.js`, presence-guarded; [l1-engine-core.md](l1-engine-core.md) §Known Process Gaps — Dev-Repo Engine-Version Snapshot Sync).
5. Regenerate `skills/magicspec/.checksums` across all tracked engine files (`scripts/generate-checksums.js`).

**No engine history files.** Version history is the git log plus `CHANGELOG.md`; the flow writes nothing under `skills/magicspec/` beyond `.version` and `.checksums`. Earlier revisions of this spec described a per-workflow `skills/magicspec/history/{workflow}.md` maintained under a "Smart History" append rule, with an Auto-Heal (C20) recreating a missing file. No such code exists: the session-log mechanism was removed on 2026-05-06, and its files had lived in the developer tree (`dev/history/`), never under `skills/magicspec/`. Two remnants are intentional and harmless — the checksum scanners still exclude a `history/` directory (§Scan Hygiene), and `update-engine-meta` still tolerates a `--workflow` argument, which once selected the history file and is no longer read. The dev-side `update-project-meta.js` keeps its own idempotent history-row rule for `.magicspec/INDEX.md`; that is project metadata, a different mechanism, and is unaffected.

**User-installation boundary (engine v2.1.98).** The flow above is the developer repository's C14: step 5 needs the manifest builder in `scripts/`, which a release does not ship, so a user installation **cannot resolve engine drift** — and must say so rather than perform half of the flow. Until v2.1.98 the write branch bumped `skills/magicspec/.version` first and only then found no builder: it printed the "this is a user installation" warning block, then `✅ Engine metadata and version updated.`, and exited 0 — with `.checksums` untouched, so the drift it was run for was still there, and every retry bumped the version again (2.1.97 → 2.1.98 → 2.1.99 in a reproduced user-installation fixture; 2.1.95 → 2.1.96 in the reporting project's own session log, whose next pre-flight still reported both files). The version is the signal Engine Upgrade Detection (`skills/magicspec/AGENT-RULES.md` §1) treats as an external engine replacement, so a local bump is indistinguishable from an upgrade to it, and the success line was false. Two emitters sent operators there: `check-prerequisites.js`'s `ENGINE_INTEGRITY` warning named `update-engine-meta` as the fix in every installation, and the `--check` failure line said the same. Fixed with one discriminator, `utils.hasEngineWriteTooling()` — the presence of `scripts/generate-checksums.js`, the probe `runGenerateChecksums()` already used; a presence check, never a `require`, so L1 keeps running with no `dev/` — consulted at three sites:

1. Write mode refuses in a user installation **before touching anything** — no bump, no sync, no manifest rewrite — prints the existing user-installation guidance and exits 1.
2. `--check` names C14 as the remedy only where it exists; a user installation is told to restore `skills/magicspec/` from the release archive and not to regenerate `.checksums`, which would mask the change.
3. The `ENGINE_INTEGRITY` warning carries `fix: null` and the restore instruction in a user installation, and keeps the C14 command in the developer repository.

The pre-commit hook (`install-hooks.js`) already worded this correctly and is unchanged. The trigger was a downstream agent's side note that `ENGINE_INTEGRITY` fired for `skills/magicspec/workflows/spec.md` and `skills/magicspec/workflows/task.md`. The cause of *that* mismatch was not established, but the reporting project's session log narrows it: the pre-flight was clean, then reported exactly those two files about 40 minutes later in the same session; the copies the agent read in between were byte-identical to the release, no edit or shell command in the log writes under `skills/magicspec/` before the agent's own `update-engine-meta` run, and the installation was byte-identical to the release again when inspected afterwards — so the two files (or the manifest) were changed and restored by something outside the agent's session. The release itself is cleared: the latest archive and every manifest since v2.1.87 match their own blobs. Until v2.1.99 the engine could not describe the difference: `modified locally` was reported alike for an edit, a line-ending conversion and a manifest swap, and no hash was recorded — see **Diagnosable drift** below. What this section fixes is the remedy path the warning leads down: the same log shows the agent following the hint — the version moved 2.1.95 → 2.1.96, the output ended with a success line, and the next pre-flight still reported both files.

**Diagnosable drift (engine v2.1.99).** An integrity finding now says how a file differs, not only that it does. `utils.describeManifestDelta(filePath, expectedHash)` returns both hashes, the file's own line-ending style (`LF`, `CRLF`, `mixed`, `none`) and whether line endings are the *whole* difference — the bytes equal the recorded content once endings are normalised, in either direction (`expectedEol` names the style the manifest's bytes use). The decode is `latin1`, so the round trip is lossless for any content, multi-byte text included, and the helper is total: an unreadable file yields `null` and the caller omits the detail, since a diagnostic must never become a second failure. Two emitters use it. `check-prerequisites.js`'s `ENGINE_INTEGRITY` message always carries both hashes as 12-hex prefixes — `'skills/magicspec/x' has been modified locally (sha256 expected …, found …).` — and names a line-endings-only difference as such: `… has been modified locally: only its line endings differ (found CRLF, the release ships LF; sha256 expected …, found …).` `update-engine-meta`'s per-file `Detected change in:` line gains a dash-separated note, `only line endings differ (found CRLF, the release ships LF)`, for a manifested file in that case and is otherwise unchanged; the hashes stay out of it, because every C14 run in the developer repository prints that line for each file it has just edited. Verdicts, exit codes and remedies are untouched — only the wording of what is reported changed — and a file that differs in both content and endings is reported as content, the endings being incidental. The DG-10 recheck keys a finding on its `code`, never its message, so the extra text cannot desynchronise revalidation.

**Deleted engine files (pre-flight).** Two checks read `skills/magicspec/.checksums`, and they disagree about a file that is gone. `update-engine-meta --check` reports a manifested file absent from disk (`Missing engine file`, non-zero exit). The `ENGINE_INTEGRITY` loop of `check-prerequisites.js` hashes only the manifested files that exist (`if (fs.existsSync(fullPath))`), so a deleted one produces no finding at all; the guard has been there since the script's first revision and no case covers it. Reproduced on an extracted release layout (engine 2.1.136): deleting `skills/magicspec/templates/plan.md` leaves the pre-flight without a warning, while appending a space to `skills/magicspec/templates/spec.md` yields `ENGINE_INTEGRITY`; deleting a module a script requires (`scripts/lib/scan-hygiene.js`) ends the pre-flight in an uncaught `MODULE_NOT_FOUND` with a stack trace and no JSON, which the workflows read as an unrecognized failure. The pre-flight is the check that runs before every workflow, and the commit-time hook that would cover the gap is absent from every installation surveyed (§Git Hook Lifecycle), so for a deletion nothing in the engine reports what the manifest knows. Several consumers of a missing file already degrade quietly: `init.js` replaces a template it cannot find with an empty string and records a finding of severity `fix`.

**Required fix:** a manifested file absent from disk is an `ENGINE_INTEGRITY` finding of the same kind as a modified one — `'skills/magicspec/{file}' is missing locally.` — with the remedy of the installation kind (restore from the release archive in a user installation, the C14 command in the developer repository), and it makes `ok` false as a modified file does. Pre-flight and `--check` then agree on the three cases (untouched, modified, deleted), and a harness case holds that agreement ([l2-test-suite.md](l2-test-suite.md), pre-flight deletion coverage). Not specified, for want of an occurrence: a stray unmanifested file (the pre-flight does not walk the tree, and the manifested-path boundary above exists because a tree walk produced false findings); naming the engine as the likely cause when a required module fails to load.

### Scan Hygiene (Invariant 7 Parity)

Engine scripts that walk the project tree (e.g., `detect-communities.js`) MUST exclude paths ignored by `.gitignore`, in addition to the hardcoded `SKIP_DIRS` denylist. The script reads `.gitignore` at startup and derives two matcher classes:

- **Basename matchers** from directory patterns without a path separator — glob (`*tmp/` → any segment ending in `tmp`; `.*_cache/` → `.ruff_cache`, `.pytest_cache`) or plain (`node_modules/`).
- **Anchored prefixes** from glob-free directory patterns that contain a path separator (e.g., `.magicspec/wiki/`, `.magicspec/.graph-cache/`).

A directory is skipped when its basename matches a basename matcher, or its workspace-relative path falls under an anchored prefix. This prevents test fixtures and generated artifacts (e.g., `.tmp/`, `.magicspec/wiki/`) from polluting community detection and boundary-alignment metrics. The hardcoded `SKIP_DIRS` remains as a gitignore-independent floor — the two are unioned, never mutually exclusive.

**Checksum scanners (engine v2.1.87).** `generate-checksums.js` and `update-engine-meta.js` walk `skills/magicspec/` itself and were the last two tree-walking scripts not honoring this Invariant — the gap that let a stray, `.gitignore`d third-party-tool cache directory created inside `skills/magicspec/` on a developer machine (`.fallow/`) get baked into the committed `.checksums` manifest. Since the release archive is built by walking a fresh CI checkout (`.github/workflows/release.yml`), a gitignored/untracked path baked into the manifest can never be satisfied by any consumer install, and `update-engine-meta --check` (the pre-commit hook) failed unconditionally on the very first commit, with no self-heal path (`scripts/generate-checksums.js` — the only tool that can regenerate the manifest — is absent by design on consumer installs). Both scripts now union their existing `VOLATILE_STATE_FILES` / `history`-directory excludes with `utils.loadGitignore()` and `utils.BUILD_NOISE_DIRS`, the same shared floor every other scanner in this section already uses.

**Manifested-path boundary (engine v2.1.93).** The gitignore union above is authored against the *source* repo's `.gitignore` (where `skills/magicspec/` itself is git-tracked, never ignored — only stray cruft matches). `update-engine-meta.js --check` instead runs inside a **consumer's** installed repo, where `.gitignore` carries the opposite, equally legitimate meaning: the L1 contract requires every consumer to gitignore `skills/magicspec/` wholesale, since it is "installed from a release archive, not committed" (`l1-engine-core.md` §Distribution). Applying the same unconditional exclusion there matched *every* file the manifest listed, emptied the on-disk set, and reported all shipped engine files as missing — failing `--check` on every commit for any project following the documented convention (reproduced against a real consumer project). `update-engine-meta.js`'s gitignore exclusion now applies **only to a path absent from `.checksums`** — a manifested path is always checked against disk regardless of the consumer's own `.gitignore`, while an unmanifested, gitignored stray file (the original `.fallow/`-shaped case) is still excluded from triggering a false "new engine file" detection. `generate-checksums.js` needs no equivalent change: it always builds the manifest from scratch in the source repo, where this asymmetry does not arise.

### Path Matching Contract (Scope & Canonical References)

Origin: downstream field report (engine 2.1.27), reproduced upstream at 2.1.30 — scope entries and spec references were matched by literal string comparison, so natural inputs (`docs/` with trailing slash, `src/**` globs) silently matched nothing: empty scans reported as clean, EXTRACTED files demoted to INFERRED, and false `shadow_specs` orphans emitted.

**Single Matcher Invariant.** Every engine script that filters or attributes project paths against user-supplied path sets (workspace `scope` arrays from `workspace.json`, Canonical References `Path` cells) MUST resolve matches through one shared matcher exported by `skills/magicspec/scripts/utils.js`. Per-script literal `startsWith` comparison is forbidden. Consumers: `analyze-coverage.js` (scope filter and reference classification), `extract-rationale.js`, `generate-context.js`, `build-spec-graph.js` (workspace attribution — see [l2-spec-graph-memory.md](l2-spec-graph-memory.md)).

**Matching semantics** (one entry = one scope element or one `Path` cell):

| Input form | Interpretation |
| --- | --- |
| `dir` or `dir/` | The path itself and everything beneath it (trailing slash normalized away) |
| `file.ext` | Exact file match |
| `*` | Wildcard within a single path segment |
| `**` | Wildcard across any number of segments |

All matching is repo-root-relative, forward-slash normalized, case-sensitive, and anchored at the start of the entry.

**Zero-Match Guard (negative space).** A scope entry or pattern reference that matches zero existing files emits a non-blocking warning (`SCOPE_NO_MATCH` / `REF_NO_MATCH`). Silent empty result sets are forbidden — an empty scan must never be indistinguishable from a clean scan. Mirrors §Scan Hygiene: the boundary input, not the hardcoded assumption, is the source of truth.

**Pattern references in coverage.** A Canonical Reference containing glob metacharacters is a *pattern ref*: files it matches classify as EXTRACTED with spec attribution preserved. The shadow-spec orphan test for a pattern ref is "matches zero files on disk" — never a literal existence probe of the raw pattern string.

### Bloat Advisory Configuration

`check-bloat.js` thresholds are advisory defaults, not constants — legitimate spec style varies by project (downstream report: 42 specs legitimately above 300 lines produce permanent advisory noise). Defaults remain `spec 300/500` and `task 250/400` (soft/hard), overridable per project via `.magicspec/workspace.json`. Configuration contract `[REFERENCE]`:

```json
{
  "bloat": {
    "spec": { "soft": 300, "hard": 500 },
    "task": { "soft": 250, "hard": 400 }
  }
}
```

- Omitted keys fall back to defaults; a threshold set to `0` disables that signal class.
- The spec scan walks `specifications/**` recursively — parity with the finalize significance whitelist; top-level-only scanning is a defect.
- **Deployment status (engine 2.1.136):** specified, not built — `check-bloat.js` keeps the thresholds as constants and reads the top level of `specifications/` only (§Setting Parity).

### Setting Parity — a Promised Setting Needs a Reader `[ADDED]`

**The defect** (reference-mining pass, engine 2.1.136): a setting is a promise made to whoever writes its value, and a setting that no script reads breaks the promise silently — the value is accepted, nothing changes, and nothing reports it. [l1-session-continuity.md](l1-session-continuity.md) SC-1.3 states the rule for the fields of the `STATE.md` template, and `WRAPPER_BODY_DRIFT` and `PHANTOM_COMMAND` ([l2-workflow-wrappers.md](l2-workflow-wrappers.md) §6.1) state it for wrapper bodies and `/magicspec:*` commands. The settings the engine ships are the surface none of them covers, and it holds live cases, each verified against the tree at engine 2.1.136:

- **`archival.enabled`** — defined by the shipped `workspace.json` template, and `skills/magicspec/AGENT-RULES.md` §4 tells the user to set it to `false` for a project-wide disable. No script reads the `archival` section: `finalize.js` loads only `finalization`, and the archival step runs whenever the workflow is `run`. Reproduced in a throwaway project: with `"archival": { "enabled": false }`, `finalize --workflow=run` still moved a `Done` phase workbook to `archives/tasks/` and rewrote its links in `TASKS.md` and `PLAN.md`. The only other switch, `finalization.enabled`, turns off the version bump, the changelog entry and the state update with it, so a user who wants archival alone off cannot say so.
- **`archival.archiveDir`** — defined in the same block; `phase-archiver.js` builds the location from the literals `archives` and `tasks`.
- **A promised notice** — `skills/magicspec/AGENT-RULES.md` §4 says the pre-commit hook issues a non-blocking notice when `Done` phases are unarchived. The generated hook (`install-hooks.js`) runs the integrity check alone; the `--check` mode that `archive-phases.js` provides for a hook has no caller, and no revision of the hook script ever contained one.
- **The `bloat` override and the recursive scan** of §Bloat Advisory Configuration — specified since 1.6.0, built by no phase or task.

The first three arrived in one change (engine 2.0.28, whose message announces all three) and stayed unreported for five months: no engine check covers the surface. Outside this repository the same shape appears in the configuration file of an external collection of agent configurations — six keys for one skill, two read by its code, and the four unread ones the behavioural ones, among them an approval switch whose safe default reads as a safeguard that nothing implements.

**Required Fix**:

1. **Parity.** Every setting that the shipped template or shipped text defines or names has a reader. *Shipped text* is the file set Phantom Commands scans (`skills/magicspec/`, `docs/`, `README.md`). A *setting* is a key meant to change what a shipped script does: a key of the `workspace.json` template outside the workspace registry (`default` and `workspaces`, whose `description` entries are metadata the agent reads), or a dotted key path (`{section}.{key}`, deeper paths included) that a line of shipped text names together with `workspace.json`. The reader is a script under `skills/magicspec/scripts/` that consumes the value: it reads the section from the parsed file and the key from that section, directly or through a defaults table merged over it. A comment, a string or a message that merely names the key is not a read. A setting without a reader is removed from the template and the shipped text, or given its reader, in the change that finds it — it is not left to age. The converse is not a defect: a script may read a key that no shipped file names (`finalization.changelogPath` and `finalization.versionPath` today), as a body may have no wrapper ([l2-workflow-wrappers.md](l2-workflow-wrappers.md) §6).
2. **Specifications may lead; shipped files may not.** A specification can define a setting before the task that builds its reader has run (§Bloat Advisory Configuration is such a case). The rule binds the files already in users' hands.
3. **Check.** `magic.analyze` Mode C step 2 gains a third line beside Router Parity and Phantom Commands: `PHANTOM_SETTING {file}:{line} → {key} has no reader` (advisory, non-blocking). The script harness holds the same rule as a standing check over the shipped tree that fails the suite on any finding, so the repository cannot regress between ventilation runs ([l2-test-suite.md](l2-test-suite.md), shipped-text contract coverage).
4. **Scope.** The scan covers `workspace.json`, the one shipped file whose values users edit. Environment variables and executor flags named in shipped text stay outside it, on the evidence of this tree: the four `MAGIC_*` variables that shipped text names only in `skills/magicspec/AGENT-RULES.md` are switches the agent itself is told to honor, with no script to read them, and a flag scan takes an external command's flags for the engine's own (`git clone --depth 1` in `README.md`). Whether the agent can observe such a variable is a reading question for the simulation workflow's reading test (Finding Adjudication, [l2-test-suite.md](l2-test-suite.md)), not a scan.

**Resolution of the cited cases** — `Assumption (forecast)`; the status quo is dropped, since it contradicts item 1:

- `archival.enabled` is kept and given its reader, and `archival.archiveDir` is withdrawn because the location is fixed; [l2-engine-finalization.md](l2-engine-finalization.md) §4 states both.
- The notice is withdrawn from `skills/magicspec/AGENT-RULES.md` §4: the generated hook is part of the L1 contract, an installed hook keeps its old script, and nothing observable is lost by dropping a sentence the hook never honored.
- The `bloat` override keeps its design; its reader and the recursive scan are the deployment task's work.
- Runner-up: withdraw both archival settings and the sentence about the hook. Override: `/magicspec:spec amend l2-engine-finalization "withdraw the archival opt-out"`. Evidence for the winner: archival is the engine's only automatic move of user-visible files, honoring a value a user has already written costs one reader, and withdrawing the switch would leave no finer one.

**Deployment** (routed to `/magicspec:task engine`; each `skills/magicspec/` or `workflows/` change triggers C14, and `skills/magicspec/AGENT-RULES.md` is a hardlinked pair, **[C-001]**): `finalize.js` reads `archival.enabled`; the template drops `archiveDir`; `skills/magicspec/AGENT-RULES.md` §4 loses the hook sentence; `skills/magicspec/workflows/analyze.md` Mode C step 2 and its Completion Checklist gain the `PHANTOM_SETTING` line, with the matching line in `docs/analyze.md`; the harness gains the standing check and the opt-out cases; `check-bloat.js` reads the override and walks `specifications/` recursively.

### Git Hook Lifecycle — an Installed Hook Outlives Its Installer `[ADDED]`

**The defect** (reference-mining pass, engine 2.1.136; every case below reproduced in a throwaway repository). `install-hooks.js` writes `.git/hooks/pre-commit` with one unconditional `writeFileSync`, prints a success line, and nothing in the engine looks at the hook again — no check, no marker, no removal. Five consequences, four of them silent:

1. **A hook the installer did not write is destroyed.** A repository that already had a pre-commit hook has it replaced on `init`; the installer neither checks nor backs up, and its only output is the success line.
2. **"Installed" is not "will run".** With `core.hooksPath` set — which hook managers do — git never reads `.git/hooks/`. The installer still prints "installed successfully", the file exists, and a commit proceeds with no integrity check.
3. **A failed install is a success to its caller.** The `catch` prints the error and returns, so the process exits 0. `init.js` records `GIT_HOOKS_NOT_INSTALLED` when the installer exits non-zero; for a write failure (a `pre-commit` that is a directory, an unwritable hooks directory) the one handler written for this case cannot fire, and the finding never reaches the digest ([l1-engine-diagnostics.md](l1-engine-diagnostics.md) DG-1: record, do not only print).
4. **The hook outlives the engine.** The hook runs `node skills/magicspec/scripts/executor.js update-engine-meta --check` and takes any non-zero exit for drift. With `skills/magicspec/` deleted — the removal RC-12 describes — Node cannot load the executor (exit 1), and the hook prints a stack trace followed by "Engine drift detected in skills/magicspec/" and advice to restore it. Nothing drifted; the engine is absent. Every commit then fails until the user finds a file under `.git/`. [l1-sdd-reference-containment.md](l1-sdd-reference-containment.md) RC-12, `skills/magicspec/workflows/analyze.md` step 6a and `skills/magicspec/AGENT-RULES.md` §6 all say the hook leaves with the scaffold ("is removed with", "goes away with"); nothing removes it.
5. **The hook is not a dependable layer.** Of seven consumer installations and this repository, none has the hook in `.git/hooks/`, and one redirects hooks to a directory of its own whose hook does not run the check. The changelog records a release (2.1.93) that fixed a hook failing every commit of every consumer that followed the documented convention; that users deleted a hook that had blocked them is a hypothesis, not a finding. The always-on verification is pre-flight `ENGINE_INTEGRITY`, which reports a modified manifested file and, until the fix of **Deleted engine files** above, not a deleted one; the hook is a second, best-effort line at commit time.

**Required Fix** — a contract scoped to the cases above:

1. **Ownership.** The hook carries the marker line `# Magic Spec Pre-commit Hook`. The marker shows who wrote a hook, not that nobody has touched it since, so the installer separates three cases. No file: it writes the hook. A file with the marker and exactly the body being written: nothing to do, so a reinstall is idempotent. A file with the marker and any other body — an older engine's hook, or one a user extended — is replaced only after its bytes are saved beside it (`pre-commitskills/magicspec-spec.bak`, numbered when that name is taken), and the output names the copy. Everything else belongs to the user's tooling and is left alone: a file without the marker, a `pre-commit` or a `.git/hooks` that is a symbolic link (the target is someone else's file, often a tracked one), and a hooks directory that `core.hooksPath` redirects. For these the installer writes nothing, prints the one line the user adds to chain the check (`node skills/magicspec/scripts/executor.js update-engine-meta --check || exit 1`), and exits non-zero.
2. **Truthful outcome.** The success line is printed only when the file was written to a place git reads. Every failure to install exits non-zero, so the handler `init.js` already has records it.
3. **Disarm without the engine.** The hook's first act is to test for the `skills/magicspec/` directory. Absent, it prints one line — the engine is not installed here, nothing was checked, delete this file if the removal was intended — and exits 0. Present, behavior is unchanged: drift, a missing file or an unrunnable executor blocks, with the existing message. The test is for the directory, not for the executor, so a partly deleted engine still blocks and still says restore. The directory counts as absent only when it does not exist; one that cannot be inspected counts as present, because an exception to a guard falls back to the guard on doubt.
4. **RC-12 restated.** The hook is exempt from the scaffold boundary, and it does not vanish with the scaffold: the exemption rests on item 3, not on a removal nothing performs.

```plaintext
BAD : hook = run the check; any non-zero exit → "Engine drift detected"          // engine deleted → blocked, wrongly named
GOOD: hook = no skills/magicspec/ → say so, exit 0
             else run the check; non-zero → block (drift, or an engine too broken to run)
```

**Not specified, for want of an occurrence (RA-2):** an `uninstall` subcommand (removal is deleting one marked file); a pre-flight check for a missing or ineffective hook (the integrity check itself runs at every pre-flight, and no case of harm from an absent hook is on record); telling drift from a crash by exit code (the hook cannot, and the cases above do not need it); refreshing an old hook after an engine upgrade (item 1 makes a reinstall over an old hook safe, nothing makes the reinstall happen); closing the window between the ownership check and the write (one user, one command). Each may be specified when a case is recorded.

**Resolution of item 3** — `Assumption (forecast)`; candidates walked through the five scenarios. The status quo blocks a user who removed the engine on purpose at every commit (Boundary) and is dropped. A corrected message that still blocks is accurate, but the removal still costs a hunt through `.git/`, and the accidental case (`git clean -x` deleting the ignored `skills/magicspec/`) gains nothing the next `/magicspec:*` run would not report louder, so it is dropped. Disarm: its worst case is an accidental deletion going unremarked at commit time, and that commit holds nothing of `skills/magicspec/` (consumers gitignore it, [l1-engine-core.md](l1-engine-core.md) §Distribution) or records the deletion where `git status` shows it, while the next workflow fails at once. Disarm wins. Runner-up: the corrected message. Override: `/magicspec:spec amend l2-engine-automation "the hook blocks when the engine is absent"`.

**Deployment** (routed to `/magicspec:task engine`; each `skills/magicspec/` change triggers C14): `install-hooks.js` gains the marker test, the `core.hooksPath` test, the exit codes and the guard in the hook body; `skills/magicspec/workflows/analyze.md` step 6a and `skills/magicspec/AGENT-RULES.md` §6 (a hardlinked pair, **[C-001]**) lose the "removed with the scaffold" claim; the harness gains the cases of [l2-test-suite.md](l2-test-suite.md). An installed hook keeps its old script (§Setting Parity), so an existing installation gains the disarm only by reinstalling, which item 1 makes safe.

### Coverage Denominator Scope (EXEMPT classification)

**The defect** (ventilation, 2026-08-06): `analyze-coverage.js` classifies every scanned file — including `.magicspec/`'s own bookkeeping output (`PLAN.md`, `TASKS.md`, `STATE.md`, `CONTEXT.md`, `CHANGELOG.md`, `RETROSPECTIVE.md`, and every archived phase journal under `archives/`) — through the same EXTRACTED/INFERRED/AMBIGUOUS/UNCOVERED pipeline as implementation source. None of these files are ever meant to appear in a spec's Canonical References — they are the SDD process's own state, not a coverage subject — so they land UNCOVERED by construction and drag the reported percentage down as project history accumulates. Reproduced on this repository's own `engine` workspace: 85.4% reported, 17 of 25 UNCOVERED files being archived phase journals alone.

**Required Fix**: introduce a fifth classification, `EXEMPT`, applied before the existing four-step `classifyFile()` pipeline runs. A file whose basename is one of `PLAN.md` / `TASKS.md` / `STATE.md` / `CONTEXT.md` / `CHANGELOG.md` / `RETROSPECTIVE.md` / `INDEX.md` / `RULES.md` under `.magicspec/`, or whose path contains an `archives` segment under `.magicspec/`, classifies `EXEMPT` and is excluded from `total`, `coveredCount`, and `coveragePercent` — but still appears in `--json` output (its own `coverage[]` entry, and a `summary.exempt` count) so the exclusion is auditable, not a silent drop.

```plaintext
BAD : total = extracted + inferred + ambiguous + uncovered
      // PLAN.md, archived phase journals, etc. inflate `uncovered`
GOOD: total = extracted + inferred + ambiguous + uncovered   // EXEMPT excluded entirely
      summary.exempt = counts.exempt                          // reported, not hidden
```

`.magicspec/{ws}/specifications/*.md`, `workspace.json`, and active (non-archived) `tasks/*.md` remain **not** exempted — `specifications/` in particular still classifies mostly INFERRED/EXTRACTED, not UNCOVERED (32/32 specs matched on this repository's own `engine` workspace), so widening the exemption there remains unevidenced.

`INDEX.md` and `RULES.md` join the EXEMPT set as of this revision. The 1.7.0 text left them out on the same "not evidenced as needed" reasoning that scoped the original defect to the bookkeeping/journal set — but a follow-up ventilation pass (2026-08-07) reproduced `.magicspec/engine/INDEX.md` itself landing `UNCOVERED` on this repository's own registry: the identical failure mode (a file that structurally can never appear in a spec's Canonical References counting against `coveragePercent`) the bookkeeping/journal exemption exists to prevent. `INDEX.md` and `RULES.md` are registry/constitution files, never a coverage subject any more than `PLAN.md` or `TASKS.md` are — the earlier exclusion undercounted the exemption's own scope rather than deliberately narrowing it.

**Parallel doc update required**: `skills/magicspec/workflows/analyze.md` §Confidence Taxonomy documents the same four-level enum and states `coverage_percent = (EXTRACTED + INFERRED) / total * 100` verbatim — an L1 engine file, out of this spec's write scope but stale the moment `EXEMPT` ships. The implementing task MUST add the `EXEMPT` row to that table and note it is excluded from `total` entirely (not merely from the numerator, unlike AMBIGUOUS), alongside the code change (C14 applies — `skills/magicspec/` content changed).

### DESIGN_DEBT_PENDING — Plan-Complete Structural Predicate `[ADDED]`

**The defect** (field report, engine 2.1.71; concept authority [l1-session-continuity.md](l1-session-continuity.md) §Terminal-Row Recognition): `check-prerequisites.js`'s `DESIGN_DEBT_PENDING` gate only evaluates the Backlog once a `planComplete` pre-check passes, and that check currently requires the `## Active Phases` section of `TASKS.md` to reduce, verbatim, to the empty-marker line `*None ...*`:

```js
const planComplete = Boolean(activePhasesMatch) && /^\*None\b/m.test(activePhasesMatch[1].trim());
```

`phase-archiver.js` (`updateTasksIndex()`, governed by [l2-engine-finalization.md](l2-engine-finalization.md) §2) rewrites a finished phase row's status to `` `Done (Archived)` `` in place — it never relocates the row out of whatever section it already occupies. The canonical `tasks.md` template defines exactly one phase table, under `## Active Phases`, with no second "completed" section for rows to move into. So under the shipped template, once a single phase has ever been archived, `## Active Phases` permanently contains a table row instead of the literal empty marker, and `planComplete` can never evaluate `true` again for the remaining life of the workspace — `DESIGN_DEBT_PENDING` is structurally unreachable regardless of Backlog content.

**Required Fix**: recognize completion by row status, not by literal section text — every row in `## Active Phases` carries a terminal status (`Done`, `Done (Archived)`, `Cancelled`) and none carries a non-terminal one (`Todo`, `In Progress`, `Blocked`); the empty-marker form remains one valid terminal case (zero rows), not the only one.

```plaintext
BAD : planComplete = section trims to literal `*None ...*`
GOOD: planComplete = section has zero rows, OR every row's `Status` cell is one of
      Done / Done (Archived) / Cancelled, with no Todo / In Progress / Blocked row present
```

**Regression coverage**: the existing `DESIGN_DEBT_PENDING` fixtures in the test harness assume a hand-split `## Active Phases` (empty) + `## Completed Phases` (archived rows) layout that no shipped script produces — that structure is a local, undocumented convention in this engine's own workspace, not the canonical single-table `tasks.md` shape. The fixtures must gain a case built against the canonical single-table layout (one `## Active Phases` table whose only rows are `Done (Archived)`) alongside the existing two-section case, so the suite exercises the structure the shipped template actually generates.

#### Zero-Row Vacancy — the branch the normative line specified and the implementation did not build `[AMENDED]`

The `GOOD` line above reads *"planComplete = section has **zero rows**, OR every row's `Status` cell is ... terminal"*. The shipped predicate built the second disjunct and, for the first, substituted the literal marker: zero rows counted as complete **only when spelled `*None ...*`**. A section left genuinely vacant matched neither branch and fell through to "cannot determine", so `DESIGN_DEBT_PENDING` never reached its Backlog evaluation. Two shapes reach that state in practice — the hand-split `## Active Phases` + `## Completed Phases` layout (this engine's own workspace convention) once every row has moved across, and a table cleared outright.

The implementation recorded the narrowing as deliberate, in a code comment: *"absence of a recognizable row or marker still resolves to cannot determine"*. The rule it states is sound and worth keeping — but it had no counterpart in either spec, so code and contract disagreed with no surface on which to notice it. That is the reusable lesson here: a guard that narrows a specified predicate is itself a specification change, and a comment is not where it lives.

**Required Fix**: recognize a **vacant** section — zero phase rows, with nothing remaining but table scaffolding (header/separator rows) or whitespace — as a third positive terminal case alongside the marker and the all-terminal table. Vacancy MUST stay narrower than "nothing matched": content present but unrecognized continues to resolve to "cannot determine", because this predicate gates a check that raises a HALT.

```plaintext
BAD : zero rows counts only when spelled `*None ...*`; a cleared section is "cannot determine"
GOOD: zero rows counts however it is spelled — marker, vacant section, or header-only table;
      only content the predicate could not parse is "cannot determine"
```

**Regression coverage**: one harness case pinning all three halves together — a vacant section under a populated `## Completed Phases` fires; a header-only table (same zero-row state, scaffolding left behind) fires; and unrecognized prose in the section still does **not** fire. The third assertion is the load-bearing one: without it the fix is indistinguishable from deleting the guard.
