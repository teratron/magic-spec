# Stage 60 Tasks — The Engine's Own Scenarios (Simulations Beside the Cognitive Suite)

**Phase:** 60
**Status:** Done
**Strategic Goal:** The engine has its first user scenarios, in the folder every project keeps them, so `/magicspec simulate engine` has something to run: five area files of journeys a developer takes through an installed engine, each step judged against what a specification states, beside the cognitive suite, which keeps checking the engine's own text.

**Phase notes:**

- **Tracks.** `P` pipeline, `I` intake, `S` session, `R` routing, `Q` quality — one area file each, no file shared, so the five run in parallel (C3). `W` the document paragraph, after them because it names the areas. `T` validation. `Y` the specification sync. Order: `P`, `I`, `S`, `R`, `Q` → `W01` → `T01` → `Y01`.
- **No engine code and no C14.** The phase writes project content under `.magicspec/` and one paragraph in `docs/`. No file of `skills/magicspec/` changes, so no task runs `update-engine-meta`. A task that finds the `simulate` body, the template or the findings reader unable to hold an engine scenario stops and sends the finding back to `/magicspec plan` (PL-8); it does not patch them.
- **Nothing is run in this phase.** Writing a scenario is not running it: every `Last run` reads `never` and has no step lines. The first `/magicspec simulate engine` after the phase is the run.
- **How a scenario is written** (`templates/simulation.md`, `@role:simulator-tester`; every area task follows this):
  1. *Actor*: a developer working in a project where the engine is installed. *Journey*, not guard: a scenario spans at least two commands, or one command and what a later session reads from the files it left.
  2. *Preconditions* open with the disposable project: a scratch directory outside this repository, holding its own copy of the engine folder, initialised there, plus the state the scenario needs. Nothing runs against this repository's own state folder (SM-6, §5.4 of the specification). Scripts of the copy run from the copy, never the repository's scripts.
  3. *Steps* are `{action} → expect: {observable outcome}`. A step names what the person types, sees or finds in a project file (`STATE.md`, `PLAN.md`, `TASKS.md`, `INDEX.md`, `RULES.md`), never a script, a subcommand, a function or a `.js` file. Each expectation ends with a tag: `(printed)` when the outcome is a line or file an engine script produces unchanged (a handoff line, a routing line, a registry row), `(composed)` when the agent writes it from a workflow body (a briefing, a form, a `[DR]` line, a specification). The tag lets a run choose live or traced without reading code, and keeps the agent that judges an outcome from being the one that composed it (§5.4).
  4. *Verifies* cites `{file}.md §{section} {identifier}` — `l1-pipeline-stages.md §3 PS-1`, or a heading where no identifier exists. A step whose expectation no specification states is not written (SM-2): it is recorded in the task's `Changes` as a specification gap. An L2 specification is cited only where no L1 states the behaviour, and the task says so in `Changes`.
  5. *Variants*: at least one per scenario — the control that shows the expectation is not a blanket rule (edge input, error path, permission boundary or interruption).
  6. *No restatement of the suite.* Before writing, search `tests/suite/` for the behaviour; a step that would only repeat a case is left out and the cases checked are listed in `Changes`. A scenario never cites a suite case.
  7. *Identifiers* are fixed by range so parallel tasks cannot collide: `P` S-1 to S-3, `I` S-4 to S-6, `S` S-7 and S-8, `R` S-9 and S-10, `Q` S-11 and S-12.
- **Area check (AC)** — the check every area task's `Verify` line applies to its file: (a) `.magicspec/engine/simulations/{area}.md` exists, begins `# {Area}` and holds exactly the scenarios the task lists, in order; (b) each scenario has `**Actor:**`, `**Verifies:**`, `**Preconditions:**`, numbered `**Steps:**` each carrying `→ expect:` and a tag, `**Variants:**` and `**Last run:** never`; (c) for each `Verifies` citation, `grep -n "{identifier}" .magicspec/engine/specifications/{file}.md` is not empty; (d) `node -e "console.log(require('./skills/magicspec/scripts/lib/simulation-findings').readSimulationFindings('.magicspec/engine').length)"` prints `0`; (e) the file names no script, subcommand, function or `.js` file.
- **Counts the plan states differently.** The plan's scenario list enumerates twelve scenarios (3 + 3 + 2 + 2 + 2) and its prose says thirteen; the list is what the tasks follow. The plan estimates five to seven tasks; validation and the specification sync make eight. Neither changes the phase's membership, so neither goes back to `plan` (PL-8).
- **Surfaced at decomposition, not blocking.** `l1-product-simulation.md` SM-7 hands a failed scenario step to `/magicspec fix`, and `finalize` prints that command; `l1-fix-command.md` FX-10 makes `/magicspec-dev fix` the entry for error feedback about the engine in this repository, and its input table lists the report of `/magicspec-dev test` but no scenario finding. The two statements leave open which command repairs a failure of the engine's own scenarios here. Forecast (DA-10): the scenarios and the first run do not depend on it, a stall would cost the phase and a wording patch costs one line, so the phase proceeds. `W01` states the route as each specification states it and claims nothing between them; `Y01` records the gap as an open finding with its one next step, `/magicspec spec amend l1-fix-command.md`. `[DR] Decomposed in full, route recorded as an open finding — lowest worst case (DA-10). (Override: /magicspec plan engine "resolve which command repairs a failure of the engine's own scenarios")`.
- **Task Instruction Review (PQ-6).** `@role:prompt-engineer` reviewed this workbook before it was written. Verdict: PASS-WITH-REWRITES. Rewrites applied inline: the identifier ranges (note 7) so five parallel tasks cannot write the same `S-n`; the area check made one defined text that every area `Verify` names, instead of five drifting copies; the count mismatch and the repair-route gap moved into notes of their own, out of the task bodies, so a task reads as one instruction.
