# 🪄 Magic Spec

![GitHub Release](https://img.shields.io/github/v/release/teratron/magic-spec)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](./LICENSE)

## 📖 Description

**The Specification-Driven Development (SDD) Operating System for AI Coding Agents.**

`magic-spec` installs a structured pipeline — *Thought → Spec → Task → Run → Code* — directly into any project, regardless of the tech stack. It acts as a set of **markdown-based workflow instructions** for AI coding agents (Cursor, Windsurf, Claude Code, Gemini CLI, and others), enforcing a deterministic process that ensures the AI fully understands the problem before writing code.

```plaintext
💡 Idea  →  📋 Specification  →  🗺️ Plan & Task →  ⚡ Run  →  🚀 Code
```

### What Gets Installed

```plaintext
your-project/
├── .agents/skills/magicspec/   # The whole SDD engine as one skill (read-only): router, workflows, scripts
├── .claude/skills/magicspec    # Claude Code reads its own folder: a link to the same skill
├── .claude/rules/magicspec.md  # The always-on rule, generated by init (a copy of the skill's AGENT-RULES.md)
├── .claude/commands/magicspec/ # One entry per command: /magicspec:spec, /magicspec:task, ...
└── .magicspec/                 # Your Design Workspace (INDEX.md, RULES.md, PLAN.md)
```

> [!NOTE]
> **One skill, seven commands.** Everything lives in a single folder, `skills/magicspec/`. A host loads its router (`SKILL.md`), which sends a command to the workflow body under `workflows/`. What a host needs outside the folder (the always-on rule, the command entries, the link to the skill) is generated from it by `init --host=<name>` and carries a marker, so `remove` deletes exactly that and nothing of yours.

> [!TIP]
> **Magic Workspaces**: Multiple isolated design environments within a single repo (e.g., `.magicspec/engine/`, `.magicspec/web/`). See [SDD Philosophy](./docs/conception.md) for details.

## 📦 Installation

Works with **any project** — Rust, Go, Python, JavaScript, C++, or anything else. The engine needs Node.js to run its scripts and adds nothing to your project's build.

### Supported Hosts

Locations verified against each host's own documentation (2026-10-28):

| Host | Skill folder | Always-on rule | Commands |
| --- | --- | --- | --- |
| Claude Code | `.claude/skills/magicspec` | `.claude/rules/magicspec.md` | `/magicspec:<command>`, from `.claude/commands/magicspec/` |
| Codex | `.agents/skills/magicspec` | a pointer block in `AGENTS.md` | `$magicspec <command>` through the router (no per-project command entry) |
| Qwen Code | `.agents/skills/magicspec` (or `.qwen/skills/magicspec`) | `.qwen/rules/magicspec.md` | `/magicspec:<command>`, from `.qwen/commands/magicspec/` |

### 🤖 Install via AI Agent (Recommended)

Copy and paste this prompt directly into your AI coding assistant (Claude Code, Codex, Qwen Code, etc.) in your target project:

````markdown
Install and configure Magic Spec in this project from https://github.com/teratron/magic-spec:

1. Ask me before proceeding:
   - Version: Stable release (from GitHub Releases) or latest current (from the master branch)?
   - Hosts to configure: any of claude, codex, qwen.

2. Fetch the release archive and copy its `skills/magicspec/` folder into the project, at the skills folder of the first selected host
   (`.claude/skills/` for Claude Code, `.agents/skills/` for Codex and Qwen Code). Do not copy anything else.

3. Run, from the project root, with the folder you just placed:
   node <skills folder>/magicspec/scripts/executor.js init --host=<comma-separated hosts>

   It creates the SDD workspace, writes the always-on rule, the command entries and the links each host needs,
   installs the pre-commit hook, and prints the .gitignore lines to add.

4. Add the printed lines to .gitignore, then run:
   node <skills folder>/magicspec/scripts/executor.js check-prerequisites
````

### Manual Installation

If you prefer installing manually without an AI assistant:

#### Option A: Download from GitHub Releases

1. Go to [Releases](https://github.com/teratron/magic-spec/releases/latest).
2. Download `magic-spec-vX.Y.Z.zip` and extract it.
3. Copy the `skills/magicspec/` folder of the archive into your host's skills folder (see the table above).
4. From your project root, run `init` for your hosts:

```bash
node .agents/skills/magicspec/scripts/executor.js init --host=codex
node .claude/skills/magicspec/scripts/executor.js init --host=claude,codex
```

#### Option B: Manual Clone

```bash
# Clone just the needed folder
git clone --depth 1 https://github.com/teratron/magic-spec.git _magic_tmp
mkdir -p .agents/skills && cp -r _magic_tmp/skills/magicspec .agents/skills/
rm -rf _magic_tmp
node .agents/skills/magicspec/scripts/executor.js init --host=claude,codex
```

### Post-Install: `.gitignore`

Add these entries to your `.gitignore` — the engine and what is generated from it are installed dependencies, like `node_modules/`:

```gitignore
# SDD engine (installed skill and its generated projections)
/.agents/skills/magicspec/
/.claude/skills/magicspec/
/.claude/rules/magicspec.md
/.claude/commands/magicspec/
/.qwen/rules/magicspec.md
/.qwen/commands/magicspec/

## Generated artifacts
/.magicspec/graph/
/.magicspec/*cache*/
```

> [!TIP]
> **Vendoring**: To commit the engine into your repo (so teammates get it without reinstalling), simply omit the engine entries from `.gitignore`. A project whose `.gitignore` still lists the earlier graph paths (`/.magicspec/*graph*.*`, `/.magicspec/wiki/`) can keep them until the first `export-wiki` run has moved the files into `.magicspec/graph/`.

### Removal

```bash
node .agents/skills/magicspec/scripts/executor.js remove --dry-run   # list what would go
node .agents/skills/magicspec/scripts/executor.js remove             # delete the marked projections, the hook and the folder
```

`remove` deletes only what carries the engine's marker, keeps your own files and your `.magicspec/` workspace, and deletes nothing in a product manifest, because it never read one.

## 🔄 Updating

Magic Spec includes a built-in upgrade-detection rule (`skills/magicspec/AGENT-RULES.md §1`). After you replace the skill folder with a newer release, the next `/magicspec:*` invocation compares the folder's `.version` against the `**Engine Version:**` snapshot in `.magicspec/INDEX.md`; on a mismatch it surfaces the drift and recommends `/magicspec:analyze` to ratify the upgrade, then proceeds — no blocking prompt. No network calls, no hidden cache — purely local.

> [!IMPORTANT]
> **Coming from 2.x?** 3.0 changes where the engine lives (one skill folder), the command names (`/magicspec:<command>`) and the state folder (`.magicspec/`). Install the new folder and run `migrate` once — see [Migrating from 2.x](./docs/migration.md). Until then every other command stops with the same instruction.

To update:

1. Download the new release archive from [Releases](https://github.com/teratron/magic-spec/releases/latest).
2. Replace the `magicspec` skill folder in your project with the archive's `skills/magicspec/`; your `.magicspec/` is untouched.
3. Run `init --host=<your hosts>` again — it regenerates any projection that fell behind (a stale one is reported as `PROJECTION_STALE` until then).
4. Run any `/magicspec:*` command — the agent surfaces the drift and recommends `/magicspec:analyze` to ratify the upgrade (run it when ready).

## 🔗 Integration

Magic Spec is designed to be agent-agnostic: the skill is plain Markdown plus Node scripts, and the generated entries only point at it.

- **Skill (`skills/magicspec/`)**: the one source. A host that supports skills loads `SKILL.md`; the command grammar is `magicspec <command> [args]`.
- **Rule (`AGENT-RULES.md`)**: behavioral instructions loaded into the agent's context at the start of every session; `init` copies it where each host reads rules, or points at it from `AGENTS.md`.
- **Commands (generated)**: slash-command entries for the hosts that have a per-project command folder.

For the host table with its sources and the mechanics of each projection, see the [Distribution Guide](./docs/distribution.md).

## 💬 Usage

### Natural Language

Talk to your AI agent naturally — it will route to the correct workflow:

- *"Create a spec for user authentication"* → **Specification** workflow
- *"Build an implementation plan"* → **Task & Plan** workflow
- *"Execute the next task"* → **Run** workflow
- *"Add a rule: always use Inter font"* → **Rule** workflow
- *"Run a project audit"* → **Analyze** workflow

### Slash Commands

All core workflows are available as slash commands with optional arguments:

| Command | Purpose |
| --- | --- |
| `/magicspec:spec` | Create or update specifications |
| `/magicspec:task` | Generate implementation plan and tasks |
| `/magicspec:run` | Execute tasks from the plan |
| `/magicspec:rule` | Add or amend project conventions |
| `/magicspec:analyze` | Audit project health and detect drift |
| `/magicspec:graph` | Build and analyze the specification knowledge graph |
| `/magicspec:status` | Resume briefing: position, progress, blockers, next command (read-only) |

#### Commands with Arguments

Each command accepts optional arguments to scope the operation to a specific **workspace** or provide a **directive**:

```bash
# No arguments — operates across all workspaces
/magicspec:spec
/magicspec:task
/magicspec:run

# Workspace-scoped
/magicspec:task engine                     # Plan only for the "engine" workspace
/magicspec:analyze engine                  # Analyze only the "engine" workspace

# With directive (quoted text)
/magicspec:task "decompose phase-2"        # Guided planning with focus
/magicspec:run "T-1A01"                    # Execute a specific task by ID
/magicspec:run "phase-2"                   # Execute all tasks in a phase
/magicspec:analyze "check API coverage"    # Focused analysis on a specific area

# Workspace + directive
/magicspec:run engine "phase-1"            # Execute phase 1 in "engine" workspace
/magicspec:task engine "only new specs"    # Plan only new specs in "engine" workspace
```

> [!NOTE]
> **For AI IDE users (Cursor, Windsurf, Claude Code, etc.):** When you type `/` in the chat, a dropdown list of available commands appears and selecting one immediately executes it **without arguments**. If you need to pass arguments (workspace name, task ID, directive), **type the full command manually** instead of selecting from the dropdown.
