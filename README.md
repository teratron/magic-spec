# 🪄 Magic Spec

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](./LICENSE)

## 📖 Description

**The Specification-Driven Development (SDD) Operating System for AI Coding Agents.**

`magic-spec` installs a structured pipeline — *Thought → Spec → Task → Run → Code* — directly into any project, regardless of the tech stack. It acts as a set of **markdown-based workflow instructions** for AI coding agents (Cursor, Windsurf, Claude Code, Gemini CLI, and others), enforcing a deterministic process that ensures the AI fully understands the problem before writing code.

```plaintext
💡 Idea  →  📋 Specification  →  🗺️ Plan & Task →  ⚡ Run  →  🚀 Code
```

### What Gets Installed

```plaintext
your-project/
├── .agents/skills/magicspec/   # The whole SDD engine as one skill (read-only): router, workflows, scripts
├── .claude/skills/magicspec    # Claude Code reads its own folder: a link to the same skill
├── .claude/rules/magicspec.md  # The always-on rule, generated by init (a copy of the skill's AGENT-RULES.md)
└── .magicspec/                 # Your Design Workspace (INDEX.md, RULES.md, PLAN.md)
```

> [!NOTE]
> **One skill, one command.** Everything lives in a single folder, `skills/magicspec/`. You type `/magicspec <command> [argument]`; the host loads the router (`SKILL.md`), which sends the command to the workflow body under `workflows/`. No per-command entry is written into your project. What a host needs outside the folder (the always-on rule and the link to the skill) is generated from it by `init --host=<name>` and carries a marker, so `remove` deletes exactly that and nothing of yours.

> [!TIP]
> **Magic Workspaces**: Multiple isolated design environments within a single repo (e.g., `.magicspec/engine/`, `.magicspec/web/`). See [SDD Philosophy](./docs/conception.md) for details.

## 📦 Installation

Works with **any project** — Rust, Go, Python, JavaScript, C++, or anything else. The engine needs Node.js 18 or newer to run its scripts (it is developed and tested on the current LTS) and adds nothing to your project's build.

### Supported Hosts

Locations verified against each host's own documentation (2026-10-28):

| Host | Skill folder | Always-on rule | How you type a command |
| --- | --- | --- | --- |
| Claude Code | `.claude/skills/magicspec` | `.claude/rules/magicspec.md` | `/magicspec <command> [argument]` |
| Codex | `.agents/skills/magicspec` | a pointer block in `AGENTS.md` | `$magicspec <command> [argument]` |
| Qwen Code | `.agents/skills/magicspec` (or `.qwen/skills/magicspec`) | `.qwen/rules/magicspec.md` | `/magicspec <command> [argument]` |

A bare `/magicspec` (or `/magicspec help`) lists the commands and offers them to run; a command given without the argument it needs asks for it.

### 🤖 Install via AI Agent (Recommended)

Copy and paste this prompt directly into your AI coding assistant (Claude Code, Codex, Qwen Code, etc.) in your target project:

````markdown
Install and configure Magic Spec in this project from https://github.com/teratron/magic-spec.
Ask me only what step 1 lists (and relay the one consent question a 2.x migration asks); do everything else yourself and stop at the first failure.

1. Ask me two things, and nothing else:
   - Version: a stable release (from GitHub Releases) or the current master branch?
   - Hosts to configure: any of claude, codex, qwen.

2. Check the runtime: run `node --version`. If it is older than 18, stop and tell me that Node.js 18 or newer is needed.

3. Look for an installed engine before you change anything:
   - A `magicspec` skill folder already in a skills folder (.claude/skills, .agents/skills, .qwen/skills): read its `.version`.
     A 3.x folder means this is an update: replace the folder with the new one, keep `.magicspec/`.
   - A `.magic/` folder or a `.design/` folder: this is a 2.x project. Install the new folder beside it (steps 4 and 5), then
     run `/magicspec migrate` instead of `init`. If the host cannot invoke the skill, run
     `node <skills folder>/magicspec/scripts/executor.js migrate`, show me the plan, and add `--apply` only if I say yes.

4. Fetch the archive into a temporary folder outside the project and copy only its `skills/magicspec/` folder.
   - Stable release, POSIX shell:
     V=$(curl -fsSL https://api.github.com/repos/teratron/magic-spec/releases/latest | sed -n 's/.*"tag_name": *"v\{0,1\}\([^"]*\)".*/\1/p')
     curl -fsSL -o /tmp/magic-spec.zip "https://github.com/teratron/magic-spec/releases/download/v$V/magic-spec-v$V.zip"
     unzip -q /tmp/magic-spec.zip -d /tmp/magic-spec
   - Stable release, PowerShell:
     $v = (Invoke-RestMethod https://api.github.com/repos/teratron/magic-spec/releases/latest).tag_name.TrimStart('v')
     Invoke-WebRequest "https://github.com/teratron/magic-spec/releases/download/v$v/magic-spec-v$v.zip" -OutFile "$env:TEMP\magic-spec.zip"
     Expand-Archive "$env:TEMP\magic-spec.zip" "$env:TEMP\magic-spec"
   - Current master branch: git clone --depth 1 https://github.com/teratron/magic-spec.git <temporary folder>

5. Place it and verify it: copy the folder into the skills folder of the first selected host
   (.claude/skills/ for Claude Code, .agents/skills/ for Codex and Qwen Code), then run
   node <skills folder>/magicspec/scripts/executor.js update-engine-meta --check
   If it reports a mismatch, the download is corrupt: delete the copy, fetch again once, and stop if it fails again.
   Never edit the folder after placing it.

6. Initialize (skip this on a 2.x project: the migration did it). From the project root run
   node <skills folder>/magicspec/scripts/executor.js init --host=<comma-separated hosts>
   It creates the SDD workspace, writes the always-on rule and the links each host needs, installs the
   pre-commit hook and prints the .gitignore lines to add. A non-zero exit: show me its output as it is and stop.

7. Finish: add the printed lines to .gitignore, run
   node <skills folder>/magicspec/scripts/executor.js check-prerequisites
   and end with one line telling me to type `/magicspec help` next. Do not commit anything.
````

### Manual Installation

If you prefer installing manually without an AI assistant:

#### Option A: Download from GitHub Releases

1. Go to [Releases](https://github.com/teratron/magic-spec/releases/latest).
2. Download `magic-spec-vX.Y.Z.zip` and extract it.
3. Copy the `skills/magicspec/` folder of the archive into your host's skills folder (see the table above).
4. From your project root, run `init` for your hosts:

```bash
node .agents/skills/magicspec/scripts/executor.js init --host=codex
node .claude/skills/magicspec/scripts/executor.js init --host=claude,codex
```

#### Option B: Manual Clone

```bash
# Clone just the needed folder
git clone --depth 1 https://github.com/teratron/magic-spec.git _magic_tmp
mkdir -p .agents/skills && cp -r _magic_tmp/skills/magicspec .agents/skills/
rm -rf _magic_tmp
node .agents/skills/magicspec/scripts/executor.js init --host=claude,codex
```

### Post-Install: `.gitignore`

Add these entries to your `.gitignore` — the engine and what is generated from it are installed dependencies, like `node_modules/`:

```gitignore
# SDD engine (installed skill and its generated projections)
/.agents/skills/magicspec/
/.claude/skills/magicspec/
/.claude/rules/magicspec.md
/.qwen/rules/magicspec.md

## Generated artifacts
/.magicspec/graph/
/.magicspec/*cache*/
```

> [!TIP]
> **Vendoring**: To commit the engine into your repo (so teammates get it without reinstalling), omit the engine entries from `.gitignore` **and** add the engine folder to `.gitattributes` — for example `/.agents/skills/magicspec/** -text`. Without it, a teammate whose Git converts line endings on checkout (the Windows default, `core.autocrlf=true`) gets CRLF copies, and the integrity check reports every engine file as modified at every commit. `init` prints the exact lines for your layout. A project whose `.gitignore` still lists the earlier graph paths (`/.magicspec/*graph*.*`, `/.magicspec/wiki/`) can keep them until the first `export-wiki` run has moved the files into `.magicspec/graph/`.

### Removal

```bash
node .agents/skills/magicspec/scripts/executor.js remove --dry-run   # list what would go
node .agents/skills/magicspec/scripts/executor.js remove             # delete the marked projections, the hook and the folder
```

`remove` deletes only what carries the engine's marker, keeps your own files and your `.magicspec/` workspace, and deletes nothing in a product manifest, because it never read one.

## 🔄 Updating

Magic Spec includes a built-in upgrade-detection rule (`skills/magicspec/AGENT-RULES.md §1`). After you replace the skill folder with a newer release, the next `/magicspec <command>` invocation compares the folder's `.version` against the `**Engine Version:**` snapshot in `.magicspec/INDEX.md`; on a mismatch it surfaces the drift and recommends `/magicspec analyze` to ratify the upgrade, then proceeds — no blocking prompt. No network calls, no hidden cache — purely local.

> [!IMPORTANT]
> **Coming from 2.x?** 3.0 changes where the engine lives (one skill folder), how commands are typed (`/magicspec <command>`) and the state folder (`.magicspec/`). Install the new folder and run `/magicspec migrate` once — see [Migrating from 2.x](./docs/migration.md). Until then every other command stops with the same instruction.

To update:

1. Download the new release archive from [Releases](https://github.com/teratron/magic-spec/releases/latest).
2. Replace the `magicspec` skill folder in your project with the archive's `skills/magicspec/`; your `.magicspec/` is untouched.
3. Run `init --host=<your hosts>` again — it regenerates any projection that fell behind (a stale one is reported as `PROJECTION_STALE` until then).
4. Run any `/magicspec <command>` command — the agent surfaces the drift and recommends `/magicspec analyze` to ratify the upgrade (run it when ready).

## 🔗 Integration

Magic Spec is designed to be agent-agnostic: the skill is plain Markdown plus Node scripts, and the generated entries only point at it.

- **Skill (`skills/magicspec/`)**: the one source and the only command surface. A host that supports skills loads `SKILL.md`; the command grammar is `/magicspec <command> [argument]`.
- **Rule (`AGENT-RULES.md`)**: behavioral instructions loaded into the agent's context at the start of every session; `init` copies it where each host reads rules, or points at it from `AGENTS.md`.

For the host table with its sources and the mechanics of each projection, see the [Distribution Guide](./docs/distribution.md).

## 💬 Usage

### Natural Language

Talk to your AI agent naturally — it will route to the correct workflow:

- *"Create a spec for user authentication"* → **Specification** workflow
- *"Build an implementation plan"* → **Task & Plan** workflow
- *"Execute the next task"* → **Run** workflow
- *"Add a rule: always use Inter font"* → **Rule** workflow
- *"Run a project audit"* → **Analyze** workflow

### One Command

Every command is typed as `/magicspec <command> [argument]` (`$magicspec <command> [argument]` in Codex). Type `/magicspec` alone, or `/magicspec help`, to see the commands and pick one; `/magicspec help ru` explains them in another language.

| Command | Purpose | Argument |
| --- | --- | --- |
| `/magicspec spec` | Create or update specifications | an idea in plain words (asked for when missing) |
| `/magicspec task` | Generate implementation plan and tasks | optional: a workspace or a directive |
| `/magicspec run` | Execute tasks from the plan | optional: a workspace, a task ID or a phase |
| `/magicspec rule` | Add or amend project conventions | the rule text (asked for when missing) |
| `/magicspec analyze` | Audit project health and detect drift | optional: a workspace or a focus |
| `/magicspec graph` | Build and analyze the specification knowledge graph | optional: `visualize` |
| `/magicspec status` | Resume briefing: position, progress, blockers, next command (read-only) | optional: a workspace |
| `/magicspec migrate` | Move a 2.x project to this layout | none |
| `/magicspec help` | List the commands, explain one, offer to run it | optional: a command, a language |

A command whose argument is required asks for it when you leave it out; a command whose argument is optional runs its default and says which. There is nothing to configure: no command is written into your project.

#### Commands with Arguments

Arguments scope the operation to a **workspace** or provide a **directive**:

```bash
# No argument — runs the default
/magicspec task
/magicspec run

# Workspace-scoped
/magicspec task engine                     # Plan only for the "engine" workspace
/magicspec analyze engine                  # Analyze only the "engine" workspace

# With directive (quoted text)
/magicspec task "decompose phase-2"        # Guided planning with focus
/magicspec run "T-1A01"                    # Execute a specific task by ID
/magicspec run "phase-2"                   # Execute all tasks in a phase
/magicspec analyze "check API coverage"    # Focused analysis on a specific area

# Workspace + directive
/magicspec run engine "phase-1"            # Execute phase 1 in "engine" workspace
/magicspec task engine "only new specs"    # Plan only new specs in "engine" workspace
```

> [!NOTE]
> **Typing a command.** A host that completes skill arguments shows the hint `<command> [argument]` after `/magicspec`; the commands themselves are listed by `/magicspec help`, which also lets you pick one. Text after the command name is its argument, so the name must come first: `/magicspec spec a holiday booking feature`.
