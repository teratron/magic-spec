> Перевод на русский официального руководства Anthropic «Skill authoring best practices». Оригинал — `anthropic-skills-guide full.md` в этой же папке. Код, имена файлов и команды оставлены как в оригинале; текст внутри примеров переведён.

Хорошие скиллы — краткие, хорошо структурированные и проверенные на реальном использовании. Это руководство даёт практические решения, которые помогут писать скиллы, которые Claude находит и эффективно применяет.

Концептуальное объяснение, как работают скиллы, — в [обзоре скиллов](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview).

## Основные принципы

### Главное — краткость

[Контекстное окно](https://platform.claude.com/docs/en/build-with-claude/context-windows) — общий ресурс. Ваш скилл делит его со всем остальным, что нужно знать Claude:

* системный промпт;
* история диалога;
* метаданные других скиллов;
* сам ваш запрос.

Не каждый токен скилла расходуется сразу. При старте заранее загружаются только метаданные (имя и описание) всех скиллов. SKILL.md Claude читает, лишь когда скилл становится нужен, а дополнительные файлы — только по необходимости. Но краткость SKILL.md всё равно важна: как только Claude его загрузил, каждый токен конкурирует с историей диалога и прочим контекстом.

**Исходное допущение:** Claude уже очень умный.

Добавляйте только тот контекст, которого у Claude ещё нет. Проверяйте каждый кусок информации:

* «Claude действительно нужно это объяснение?»
* «Можно считать, что Claude это знает?»
* «Оправдывает ли этот абзац свою цену в токенах?»

**Хороший пример: кратко** (около 50 токенов):

````markdown
## Извлечь текст из PDF

Для извлечения текста используй pdfplumber:

```python
import pdfplumber

with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```
````

**Плохой пример: многословно** (около 150 токенов):

```markdown
## Извлечь текст из PDF

PDF (Portable Document Format) — распространённый формат файлов, который содержит
текст, изображения и другое содержимое. Чтобы извлечь текст из PDF, понадобится
библиотека. Библиотек для работы с PDF много, но рекомендуется pdfplumber,
потому что она проста в использовании и хорошо справляется с большинством случаев.
Сначала её нужно установить через pip. Затем можно использовать код ниже...
```

Краткая версия исходит из того, что Claude уже знает, что такое PDF и как работают библиотеки.

### Задавайте подходящую степень свободы

Соотносите степень конкретики с тем, насколько задача хрупкая и вариативная.

**Высокая свобода** (текстовые инструкции).

Когда использовать:

* допустимы разные подходы;
* решения зависят от контекста;
* подход определяется эвристиками.

Пример:

```markdown
## Порядок код-ревью

1. Проанализируй структуру и организацию кода
2. Проверь на возможные баги и пограничные случаи
3. Предложи улучшения читаемости и сопровождаемости
4. Убедись, что код соответствует соглашениям проекта
```

**Средняя свобода** (псевдокод или скрипты с параметрами).

Когда использовать:

* есть предпочтительный шаблон;
* допустимы некоторые вариации;
* поведение зависит от настроек.

Пример:

````markdown
## Сформировать отчёт

Используй этот шаблон и адаптируй по необходимости:

```python
def generate_report(data, format="markdown", include_charts=True):
    # Process data
    # Generate output in specified format
    # Optionally include visualizations
```
````

**Низкая свобода** (конкретные скрипты, мало параметров или ни одного).

Когда использовать:

* операции хрупкие и легко ломаются;
* критична единообразность;
* нужно соблюсти строгую последовательность.

Пример:

````markdown
## Миграция базы данных

Запусти ровно этот скрипт:

```bash
python scripts/migrate.py --verify --backup
```

Не меняй команду и не добавляй флаги.
````

**Аналогия:** представьте Claude роботом, который идёт по маршруту.

* **Узкий мост с обрывами по обе стороны:** безопасный путь только один. Дайте конкретные ограждения и точные инструкции (низкая свобода). Пример: миграции базы данных, которые должны выполняться строго по порядку.
* **Открытое поле без опасностей:** к успеху ведёт много путей. Дайте общее направление и доверьте Claude найти лучший маршрут (высокая свобода). Пример: код-ревью, где лучший подход определяется контекстом.

### Тестируйте на всех моделях, с которыми планируете работать

Скиллы — это надстройка над моделью, поэтому их эффективность зависит от модели под ними. Проверьте скилл на всех моделях, с которыми собираетесь его использовать.

**Что проверять на каждой модели:**

* **Claude Haiku** (быстрая, экономичная): хватает ли скиллу указаний?
* **Claude Sonnet** (сбалансированная): понятен ли скилл и эффективен ли?
* **Claude Opus** (мощные рассуждения): не объясняет ли скилл лишнего?

То, что идеально работает для Opus, для Haiku может потребовать больше деталей. Если скилл будет работать на нескольких моделях, стремитесь к инструкциям, которые хорошо работают на всех.

## Структура скилла

> **Примечание. YAML-фронтматтер:** во фронтматтере SKILL.md обязательны два поля.
>
> `name`:
>
> * не больше 64 символов;
> * только строчные латинские буквы, цифры и дефисы;
> * без XML-тегов;
> * без зарезервированных слов: «anthropic», «claude».
>
> `description`:
>
> * не может быть пустым;
> * не больше 1 024 символов;
> * без XML-тегов;
> * должно описывать, что делает скилл и когда его применять.
>
> Полное описание структуры скилла — в [обзоре скиллов](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview#skill-structure).

### Соглашения об именах

Используйте единообразные шаблоны имён, чтобы на скиллы было проще ссылаться и обсуждать их. Рассмотрите **герундий** (глагол + -ing) для имён скиллов: такая форма ясно описывает действие или возможность, которую даёт скилл.

Помните: в поле `name` допустимы только строчные буквы, цифры и дефисы.

**Хорошие имена (герундий):**

* `processing-pdfs`
* `analyzing-spreadsheets`
* `managing-databases`
* `testing-code`
* `writing-documentation`

**Допустимые альтернативы:**

* именные словосочетания: `pdf-processing`, `spreadsheet-analysis`;
* в форме действия: `process-pdfs`, `analyze-spreadsheets`.

**Избегайте:**

* расплывчатых имён: `helper`, `utils`, `tools`;
* слишком общих: `documents`, `data`, `files`;
* зарезервированных слов: `anthropic-helper`, `claude-tools`;
* разнобоя шаблонов внутри своей коллекции скиллов.

Единообразные имена помогают:

* ссылаться на скиллы в документации и в разговоре;
* с первого взгляда понимать, что делает скилл;
* упорядочивать множество скиллов и искать среди них;
* поддерживать профессиональную и цельную библиотеку скиллов.

### Как писать эффективные описания

Поле `description` позволяет Claude находить скилл. В нём должно быть и что делает скилл, и когда его применять.

> **Внимание. Всегда пишите в третьем лице.** Описание подставляется в системный промпт, и непоследовательная точка зрения может мешать обнаружению скилла.
>
> * **Хорошо:** «Обрабатывает Excel-файлы и формирует отчёты»
> * **Избегайте:** «Я могу помочь вам обработать Excel-файлы»
> * **Избегайте:** «Вы можете использовать это для обработки Excel-файлов»

**Будьте конкретны и включайте ключевые термины.** Укажите и что делает скилл, и конкретные триггеры/контексты, когда его применять.

У каждого скилла ровно одно поле description. Оно критично для выбора скилла: по нему Claude выбирает нужный скилл, возможно, из сотни с лишним доступных. Описание должно давать Claude достаточно деталей, чтобы понять, когда выбрать этот скилл, а остальной SKILL.md содержит детали исполнения.

Удачные примеры:

**Скилл обработки PDF:**

```yaml
description: Извлекает текст и таблицы из PDF-файлов, заполняет формы, объединяет документы. Применять при работе с PDF-файлами или когда пользователь упоминает PDF, формы или извлечение данных из документов.
```

**Скилл анализа Excel:**

```yaml
description: Анализирует таблицы Excel, создаёт сводные таблицы, строит графики. Применять при анализе Excel-файлов, электронных таблиц, табличных данных или файлов .xlsx.
```

**Скилл-помощник для git-коммитов:**

```yaml
description: Составляет содержательные сообщения коммитов по анализу git diff. Применять, когда пользователь просит помочь написать сообщение коммита или просмотреть подготовленные изменения.
```

Избегайте расплывчатых описаний вроде таких:

```yaml
description: Помогает с документами
```

```yaml
description: Обрабатывает данные
```

```yaml
description: Делает что-то с файлами
```

### Шаблоны постепенного раскрытия

SKILL.md служит обзором, который по мере надобности отсылает Claude к подробным материалам, — как оглавление в руководстве для новичка. Как работает постепенное раскрытие (progressive disclosure), объяснено в разделе [Как работают скиллы](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview#how-skills-work) обзора.

**Практические рекомендации:**

* держите тело SKILL.md короче 500 строк — так скилл работает лучше всего;
* приближаясь к этому пределу, выносите содержимое в отдельные файлы;
* используйте шаблоны ниже, чтобы эффективно организовать инструкции, код и ресурсы.

#### Наглядно: от простого к сложному

Простейший скилл — один файл SKILL.md с метаданными и инструкциями:

![Простой файл SKILL.md: YAML-фронтматтер и тело в markdown](https://platform.claude.com/docs/images/agent-skills-simple-file.png)

По мере роста скилла к нему можно приложить дополнительные материалы, которые Claude загружает только при необходимости:

![Приложенные справочные файлы, например reference.md и forms.md](https://platform.claude.com/docs/images/agent-skills-bundling-content.png)

Полная структура папки скилла может выглядеть так:

* `pdf/`

  * `SKILL.md`: основные инструкции (загружаются при срабатывании)

  * `FORMS.md`: руководство по заполнению форм (загружается по необходимости)

  * `reference.md`: справочник по API (загружается по необходимости)

  * `examples.md`: примеры использования (загружается по необходимости)

  * `scripts/`

    * `analyze_form.py`: вспомогательный скрипт (запускается, а не загружается)
    * `fill_form.py`: скрипт заполнения формы
    * `validate.py`: скрипт проверки

````markdown
---
name: pdf-processing
description: Извлекает текст и таблицы из PDF-файлов, заполняет формы и объединяет документы. Применять при работе с PDF-файлами или когда пользователь упоминает PDF, формы или извлечение данных из документов.

# Обработка PDF

## Быстрый старт

Извлечь текст через pdfplumber:
```python
import pdfplumber
with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```

## Расширенные возможности

**Заполнение форм**: полное руководство — в [FORMS.md](FORMS.md)
**Справочник по API**: все методы — в [REFERENCE.md](REFERENCE.md)
**Примеры**: типовые шаблоны — в [EXAMPLES.md](EXAMPLES.md)
````

Claude загружает FORMS.md, REFERENCE.md или EXAMPLES.md только когда они нужны.

#### Шаблон 2: организация по предметным областям

Если скилл охватывает несколько областей, раскладывайте содержимое по областям, чтобы не загружать нерелевантный контекст. Когда пользователь спрашивает о метриках продаж, Claude нужно прочитать только схемы по продажам, а не данные финансов или маркетинга. Так расход токенов остаётся низким, а контекст — сфокусированным.

* `bigquery-skill/`

  * `SKILL.md` (обзор и навигация)

  * `reference/`

    * `finance.md` (выручка, метрики биллинга)
    * `sales.md` (сделки, воронка)
    * `product.md` (использование API, функции)
    * `marketing.md` (кампании, атрибуция)

````markdown SKILL.md
# Анализ данных в BigQuery

## Доступные датасеты

**Финансы**: выручка, ARR, биллинг → см. [reference/finance.md](reference/finance.md)
**Продажи**: сделки, воронка, аккаунты → см. [reference/sales.md](reference/sales.md)
**Продукт**: использование API, функции, внедрение → см. [reference/product.md](reference/product.md)
**Маркетинг**: кампании, атрибуция, email → см. [reference/marketing.md](reference/marketing.md)

## Быстрый поиск

Найти конкретные метрики через grep:

```bash
grep -i "revenue" reference/finance.md
grep -i "pipeline" reference/sales.md
grep -i "api usage" reference/product.md
```
````

#### Шаблон 3: подробности по условию

Показывайте базовое содержимое, а на продвинутое давайте ссылку:

```markdown
# Обработка DOCX

## Создание документов

Для новых документов используй docx-js. См. [DOCX-JS.md](DOCX-JS.md).

## Редактирование документов

Простые правки вноси прямо в XML.

**Для режима исправлений**: см. [REDLINING.md](REDLINING.md)
**Подробности OOXML**: см. [OOXML.md](OOXML.md)
```

Claude читает REDLINING.md или OOXML.md, только когда пользователю нужны эти функции.

### Избегайте глубоко вложенных ссылок

Claude может читать файлы частично, если на них ссылаются из других файлов, на которые тоже ссылались. Встретив вложенные ссылки, Claude может использовать команды вроде `head -100`, чтобы просмотреть начало, а не читать файл целиком, — и получит неполную информацию.

**Держите ссылки на один уровень от SKILL.md.** На все справочные файлы должны вести прямые ссылки из SKILL.md — тогда Claude при необходимости прочитает их полностью.

**Плохой пример: слишком глубоко:**

```markdown
# SKILL.md
См. [advanced.md](advanced.md)...

# advanced.md
См. [details.md](details.md)...

# details.md
А вот и сама информация...
```

**Хороший пример: один уровень:**

```markdown
# SKILL.md

**Базовое использование**: [инструкции прямо в SKILL.md]
**Расширенные возможности**: см. [advanced.md](advanced.md)
**Справочник по API**: см. [reference.md](reference.md)
**Примеры**: см. [examples.md](examples.md)
```

### Длинные справочные файлы — с оглавлением

В справочные файлы длиннее 100 строк добавляйте оглавление в начало. Так Claude увидит весь объём доступной информации, даже если просматривает файл частично.

**Пример:**

```markdown
# Справочник по API

## Содержание
- Аутентификация и настройка
- Основные методы (create, read, update, delete)
- Расширенные возможности (пакетные операции, вебхуки)
- Обработка ошибок
- Примеры кода

## Аутентификация и настройка
...

## Основные методы
...
```

Тогда Claude сможет прочитать файл целиком или перейти к нужному разделу.

Как эта файловая архитектура обеспечивает постепенное раскрытие — в разделе [Среда выполнения](#среда-выполнения) ниже.

## Порядок работы и петли обратной связи

### Для сложных задач — пошаговый порядок

Разбивайте сложные операции на понятные последовательные шаги. Для особенно сложных процессов дайте чек-лист, который Claude может скопировать в свой ответ и отмечать по ходу работы.

**Пример 1: сведение результатов исследования** (для скиллов без кода):

````markdown
## Порядок сведения исследования

Скопируй этот чек-лист и отмечай прогресс:

```
Ход исследования:
- [ ] Шаг 1: Прочитать все исходные документы
- [ ] Шаг 2: Выделить ключевые темы
- [ ] Шаг 3: Перекрёстно проверить утверждения
- [ ] Шаг 4: Составить структурированное резюме
- [ ] Шаг 5: Проверить ссылки на источники
```

**Шаг 1: Прочитать все исходные документы**

Просмотри каждый документ в папке `sources/`. Отметь основные аргументы и подтверждающие данные.

**Шаг 2: Выделить ключевые темы**

Ищи закономерности между источниками. Какие темы повторяются? В чём источники сходятся или расходятся?

**Шаг 3: Перекрёстно проверить утверждения**

Для каждого важного утверждения убедись, что оно есть в исходных материалах. Отметь, какой источник подтверждает каждый пункт.

**Шаг 4: Составить структурированное резюме**

Сгруппируй выводы по темам. Включи:
- основное утверждение;
- подтверждения из источников;
- противоположные точки зрения (если есть).

**Шаг 5: Проверить ссылки на источники**

Убедись, что каждое утверждение ссылается на правильный документ. Если ссылки неполные, вернись к шагу 3.
````

Этот пример показывает, как пошаговый порядок применяется к аналитическим задачам без кода. Шаблон с чек-листом подходит для любого сложного многошагового процесса.

**Пример 2: заполнение PDF-формы** (для скиллов с кодом):

````markdown
## Порядок заполнения PDF-формы

Скопируй этот чек-лист и отмечай пункты по мере выполнения:

```
Ход задачи:
- [ ] Шаг 1: Проанализировать форму (запустить analyze_form.py)
- [ ] Шаг 2: Составить соответствие полей (отредактировать fields.json)
- [ ] Шаг 3: Проверить соответствие (запустить validate_fields.py)
- [ ] Шаг 4: Заполнить форму (запустить fill_form.py)
- [ ] Шаг 5: Проверить результат (запустить verify_output.py)
```

**Шаг 1: Проанализировать форму**

Запусти: `python scripts/analyze_form.py input.pdf`

Скрипт извлекает поля формы и их расположение и сохраняет в `fields.json`.

**Шаг 2: Составить соответствие полей**

Отредактируй `fields.json`, добавив значения для каждого поля.

**Шаг 3: Проверить соответствие**

Запусти: `python scripts/validate_fields.py fields.json`

Исправь все ошибки проверки, прежде чем продолжать.

**Шаг 4: Заполнить форму**

Запусти: `python scripts/fill_form.py input.pdf fields.json output.pdf`

**Шаг 5: Проверить результат**

Запусти: `python scripts/verify_output.py output.pdf`

Если проверка не пройдена, вернись к шагу 2.
````

Понятные шаги не дают Claude пропустить критически важную проверку. Чек-лист помогает и Claude, и вам отслеживать ход многошагового процесса.

### Встраивайте петли обратной связи

**Типовой шаблон:** запустить проверку → исправить ошибки → повторить.

Этот шаблон сильно повышает качество результата.

**Пример 1: соответствие гайду по стилю** (для скиллов без кода):

```markdown
## Порядок проверки текста

1. Напиши черновик по правилам из STYLE_GUIDE.md
2. Сверь с чек-листом:
   - проверь единообразие терминов
   - убедись, что примеры оформлены по стандарту
   - подтверди, что все обязательные разделы на месте
3. Если нашлись проблемы:
   - запиши каждую с указанием конкретного раздела
   - исправь текст
   - снова пройди чек-лист
4. Переходи дальше, только когда все требования выполнены
5. Доработай и сохрани документ
```

Здесь петля проверки построена на справочном документе вместо скриптов. «Проверяющий» — STYLE\_GUIDE.md, а Claude выполняет проверку, читая и сравнивая.

**Пример 2: редактирование документа** (для скиллов с кодом):

```markdown
## Порядок редактирования документа

1. Внеси правки в `word/document.xml`
2. **Сразу проверь**: `python ooxml/scripts/validate.py unpacked_dir/`
3. Если проверка не пройдена:
   - внимательно прочитай сообщение об ошибке
   - исправь проблемы в XML
   - снова запусти проверку
4. **Переходи дальше, только когда проверка пройдена**
5. Собери заново: `python ooxml/scripts/pack.py unpacked_dir/ output.docx`
6. Проверь получившийся документ
```

Петля проверки ловит ошибки на ранней стадии.

## Оценка и итерации

### Сначала — оценки

**Создавайте оценки (evals) ДО того, как писать объёмную документацию.** Так скилл будет решать реальные проблемы, а не описывать воображаемые.

**Разработка от оценок:**

1. **Найдите пробелы:** прогоните Claude на типовых задачах без скилла. Зафиксируйте конкретные сбои или недостающий контекст.
2. **Создайте оценки:** соберите три сценария, которые проверяют эти пробелы.
3. **Зафиксируйте базовый уровень:** замерьте, как Claude справляется без скилла.
4. **Напишите минимальные инструкции:** ровно столько, чтобы закрыть пробелы и пройти оценки.
5. **Итерируйте:** прогоняйте оценки, сравнивайте с базовым уровнем, дорабатывайте.

Такой подход гарантирует, что вы решаете реальные проблемы, а не предугадываете требования, которые могут так и не возникнуть.

**Структура оценки:**

```json
{
  "skills": ["pdf-processing"],
  "query": "Extract all text from this PDF file and save it to output.txt",
  "files": ["test-files/document.pdf"],
  "expected_behavior": [
    "Successfully reads the PDF file using an appropriate PDF processing library or command-line tool",
    "Extracts text content from all pages in the document without missing any pages",
    "Saves the extracted text to a file named output.txt in a clear, readable format"
  ]
}
```

Перевод полей примера: `query` — «Извлеки весь текст из этого PDF-файла и сохрани в output.txt»; `expected_behavior` — «успешно читает PDF подходящей библиотекой или утилитой командной строки», «извлекает текст со всех страниц документа, не пропуская ни одной», «сохраняет извлечённый текст в файл output.txt в понятном, читаемом виде».

> **Примечание.** Пример показывает оценку на данных с простой рубрикой проверки. Встроенного способа запускать такие оценки сейчас нет — пользователи могут создать собственную систему оценки. Оценки — ваш источник истины при измерении эффективности скилла.

### Разрабатывайте скиллы итеративно вместе с Claude

Самый эффективный процесс разработки скилла включает самого Claude. Работайте с одним экземпляром Claude («Claude А»), чтобы создать скилл, которым будут пользоваться другие экземпляры («Claude Б»). Claude А помогает проектировать и дорабатывать инструкции, а Claude Б проверяет их на реальных задачах. Это работает, потому что модели Claude понимают и как писать эффективные инструкции для агентов, и какая информация агентам нужна.

**Создание нового скилла:**

1. **Выполните задачу без скилла:** решите задачу с Claude А обычными промптами. По ходу вы естественным образом даёте контекст, объясняете предпочтения и делитесь знанием процедур. Замечайте, какую информацию вы даёте повторно.

2. **Выделите повторяемый шаблон:** после выполнения задачи определите, какой контекст из того, что вы давали, пригодится для похожих задач в будущем.

   **Пример:** если вы делали анализ в BigQuery, вы, возможно, давали имена таблиц, определения полей, правила фильтрации (например, «всегда исключай тестовые аккаунты») и типовые шаблоны запросов.

3. **Попросите Claude А создать скилл:** «Создай скилл, который фиксирует шаблон анализа в BigQuery, который мы только что использовали. Включи схемы таблиц, соглашения об именах и правило про фильтрацию тестовых аккаунтов».

   > **Совет.** Модели Claude изначально понимают формат и структуру скиллов. Не нужны ни специальные системные промпты, ни скилл «как писать скиллы», чтобы Claude помог их создать. Просто попросите Claude создать скилл — он сгенерирует правильно структурированный SKILL.md с подходящим фронтматтером и телом.

4. **Проверьте на краткость:** убедитесь, что Claude А не добавил лишних объяснений. Попросите: «Убери объяснение, что такое win rate, — Claude это и так знает».

5. **Улучшите информационную архитектуру:** попросите Claude А организовать содержимое эффективнее. Например: «Организуй так, чтобы схема таблиц лежала в отдельном справочном файле. Позже мы можем добавить ещё таблицы».

6. **Проверьте на похожих задачах:** используйте скилл с Claude Б (свежий экземпляр с загруженным скиллом) на смежных сценариях. Смотрите, находит ли Claude Б нужную информацию, правильно ли применяет правила, успешно ли справляется с задачей.

7. **Итерируйте по наблюдениям:** если Claude Б буксует или что-то упускает, возвращайтесь к Claude А с конкретикой: «Когда Claude использовал этот скилл, он забыл отфильтровать по дате для Q4. Может, добавить раздел о шаблонах фильтрации по датам?»

**Итерации над существующими скиллами:**

При улучшении скиллов та же иерархическая схема продолжается. Вы чередуете:

* **работу с Claude А** (эксперт, который помогает дорабатывать скилл);
* **проверку с Claude Б** (агент, который выполняет скиллом реальную работу);
* **наблюдение за поведением Claude Б** и перенос выводов обратно к Claude А.

1. **Используйте скилл в реальной работе:** давайте Claude Б (с загруженным скиллом) настоящие задачи, а не тестовые сценарии.

2. **Наблюдайте за поведением Claude Б:** отмечайте, где он буксует, где справляется, где делает неожиданный выбор.

   **Пример наблюдения:** «Когда я попросил Claude Б отчёт по продажам в регионах, он написал запрос, но забыл отфильтровать тестовые аккаунты, хотя в скилле это правило упомянуто».

3. **Возвращайтесь к Claude А за улучшениями:** покажите текущий SKILL.md и опишите, что заметили. Спросите: «Я заметил, что Claude Б забыл отфильтровать тестовые аккаунты, когда я попросил отчёт по регионам. В скилле фильтрация упомянута, но, может, недостаточно заметно?»

4. **Разберите предложения Claude А:** Claude А может предложить реорганизовать текст, чтобы правила были заметнее, использовать более сильные формулировки вроде «ОБЯЗАТЕЛЬНО фильтруй» вместо «всегда фильтруй» или перестроить раздел с порядком работы.

5. **Примените и проверьте изменения:** обновите скилл по доработкам Claude А, затем снова проверьте с Claude Б на похожих запросах.

6. **Повторяйте по мере использования:** продолжайте цикл «наблюдение — доработка — проверка», встречая новые сценарии. Каждая итерация улучшает скилл на основе реального поведения агента, а не предположений.

**Сбор обратной связи от команды:**

1. Поделитесь скиллами с коллегами и понаблюдайте, как они ими пользуются.
2. Спросите: срабатывает ли скилл, когда ожидается? Понятны ли инструкции? Чего не хватает?
3. Учтите отзывы, чтобы закрыть пробелы, которых не видно в ваших собственных сценариях.

**Почему это работает:** Claude А понимает потребности агента, вы даёте экспертизу в предметной области, Claude Б вскрывает пробелы на реальном использовании, а итеративная доработка улучшает скиллы по наблюдаемому поведению, а не по предположениям.

### Наблюдайте, как Claude ориентируется в скиллах

Итерируя над скиллами, обращайте внимание, как Claude реально ими пользуется. Смотрите на:

* **неожиданные маршруты:** читает ли Claude файлы в порядке, которого вы не предполагали? Возможно, структура не так интуитивна, как вам казалось;
* **пропущенные связи:** не переходит ли Claude по ссылкам на важные файлы? Возможно, ссылки нужно сделать явнее или заметнее;
* **чрезмерную опору на отдельные разделы:** если Claude раз за разом читает один и тот же файл, подумайте, не перенести ли это содержимое в основной SKILL.md;
* **проигнорированное содержимое:** если Claude ни разу не открывает приложенный файл, возможно, он не нужен или плохо обозначен в основных инструкциях.

Итерируйте по этим наблюдениям, а не по предположениям. Особенно важны `name` и `description` в метаданных скилла: по ним Claude решает, запускать ли скилл под текущую задачу. Убедитесь, что они ясно описывают, что делает скилл и когда его применять.

## Антипаттерны

### Не используйте пути в стиле Windows

В путях к файлам всегда используйте прямые слеши, даже в Windows:

* ✓ **Хорошо:** `scripts/helper.py`, `reference/guide.md`
* ✗ **Избегайте:** `scripts\helper.py`, `reference\guide.md`

Пути в стиле Unix работают на всех платформах, а пути в стиле Windows вызывают ошибки в Unix-системах.

### Не предлагайте слишком много вариантов

Не перечисляйте несколько подходов без необходимости:

````markdown
**Плохой пример: слишком много вариантов** (сбивает с толку):
«Можно использовать pypdf, или pdfplumber, или PyMuPDF, или pdf2image, или...»

**Хороший пример: вариант по умолчанию** (с запасным выходом):

Для сканированных PDF, где нужно OCR, используй вместо этого pdf2image с pytesseract».
````

## Продвинутый уровень: скиллы с исполняемым кодом

Следующие разделы — о скиллах, которые включают исполняемые скрипты. Если ваш скилл состоит только из инструкций в markdown, переходите к [чек-листу эффективного скилла](#чек-лист-эффективного-скилла).

### Решайте, а не перекладывайте

Пишите скрипты для скиллов так, чтобы они сами обрабатывали ошибки, а не перекладывали их на Claude.

**Хороший пример: ошибки обработаны явно:**

```python
def process_file(path):
    """Process a file, creating it if it doesn't exist."""
    try:
        with open(path) as f:
            return f.read()
    except FileNotFoundError:
        # Create file with default content instead of failing
        print(f"File {path} not found, creating default")
        with open(path, "w") as f:
            f.write("")
        return ""
    except PermissionError:
        # Provide alternative instead of failing
        print(f"Cannot access {path}, using default")
        return ""
```

(Комментарии в коде: «обработать файл, создав его, если он не существует»; «создать файл с содержимым по умолчанию вместо падения»; «дать альтернативу вместо падения».)

**Плохой пример: переложить на Claude:**

```python
def process_file(path):
    # Just fail and let Claude figure it out
    return open(path).read()
```

(Комментарий: «просто упасть, и пусть Claude разбирается».)

Параметры конфигурации тоже должны быть обоснованы и задокументированы, чтобы не появлялись «шаманские константы» (закон Оустерхаута). Если вы сами не знаете правильное значение, как его определит Claude?

**Хороший пример: код объясняет сам себя:**

```python
# HTTP requests typically complete within 30 seconds
# Longer timeout accounts for slow connections
REQUEST_TIMEOUT = 30

# Three retries balances reliability vs speed
# Most intermittent failures resolve by the second retry
MAX_RETRIES = 3
```

(Комментарии: «HTTP-запросы обычно завершаются за 30 секунд; запас по таймауту — на медленные соединения»; «три повтора — баланс надёжности и скорости; большинство случайных сбоев проходит ко второму повтору».)

**Плохой пример: магические числа:**

```python
TIMEOUT = 47  # Why 47?
RETRIES = 5  # Why 5?
```

### Давайте готовые вспомогательные скрипты

Даже если Claude мог бы написать скрипт сам, у готовых скриптов есть преимущества:

**Чем хороши вспомогательные скрипты:**

* надёжнее сгенерированного кода;
* экономят токены (код не нужно держать в контексте);
* экономят время (не нужно генерировать код);
* обеспечивают единообразие от запуска к запуску.

![Исполняемые скрипты рядом с файлами инструкций](https://platform.claude.com/docs/images/agent-skills-executable-scripts.png)

Схема выше показывает, как исполняемые скрипты работают вместе с файлами инструкций. Файл инструкций (forms.md) ссылается на скрипт, и Claude может запустить его, не загружая содержимое в контекст.

**Важное различие:** в инструкциях ясно укажите, что Claude должен:

* **запустить скрипт** (чаще всего): «Запусти `analyze_form.py`, чтобы извлечь поля»;
* **прочитать его как справку** (для сложной логики): «Алгоритм извлечения полей — в `analyze_form.py`».

Для большинства вспомогательных скриптов предпочтительнее запуск — это надёжнее и эффективнее. Как устроен запуск скриптов — в разделе [Среда выполнения](#среда-выполнения) ниже.

**Пример:**

````markdown
## Вспомогательные скрипты

**analyze_form.py**: извлекает все поля формы из PDF

```bash
python scripts/analyze_form.py input.pdf > fields.json
```

Формат вывода:
```json
{
  "field_name": {"type": "text", "x": 100, "y": 200},
  "signature": {"type": "sig", "x": 150, "y": 500}
}
```

**validate_boxes.py**: проверяет пересечения ограничивающих рамок

```bash
python scripts/validate_boxes.py fields.json
# Возвращает: "OK" или список конфликтов
```

**fill_form.py**: подставляет значения полей в PDF

```bash
python scripts/fill_form.py input.pdf fields.json output.pdf
```
````

### Используйте визуальный анализ

Если входные данные можно отрисовать как изображения, пусть Claude анализирует их:

````markdown
## Анализ разметки формы

1. Конвертируй PDF в изображения:
   ```bash
   python scripts/pdf_to_images.py form.pdf
   ```

2. Проанализируй изображение каждой страницы, чтобы найти поля формы
3. Claude видит расположение и типы полей визуально
````

> **Примечание.** В этом примере скрипт `pdf_to_images.py` нужно написать самостоятельно.

Зрение Claude помогает анализировать разметку и структуру.

### Создавайте проверяемые промежуточные результаты

Выполняя сложные открытые задачи, Claude может ошибаться. Шаблон «план — проверка — исполнение» ловит ошибки на ранней стадии: сначала Claude составляет план в структурированном формате, затем этот план проверяется скриптом, и только потом исполняется.

**Пример:** вы просите Claude обновить 50 полей формы в PDF по данным из таблицы. Без проверки Claude может сослаться на несуществующие поля, создать конфликтующие значения, пропустить обязательные поля или применить обновления неправильно.

**Решение:** используйте показанный выше порядок (заполнение PDF-формы), но добавьте промежуточный файл `changes.json`, который проверяется до применения изменений. Порядок становится таким: анализ → **создание файла плана** → **проверка плана** → исполнение → проверка результата.

**Почему этот шаблон работает:**

* **ловит ошибки рано:** проверка находит проблемы до применения изменений;
* **проверяется машиной:** скрипты дают объективную проверку;
* **обратимое планирование:** Claude может переделывать план, не трогая оригиналы;
* **понятная отладка:** сообщения об ошибках указывают на конкретные проблемы.

**Когда применять:** пакетные операции, разрушительные изменения, сложные правила проверки, операции с высокой ценой ошибки.

**Совет по реализации:** делайте скрипты проверки многословными, с конкретными сообщениями об ошибках, например: «Field 'signature\_date' not found. Available fields: customer\_name, order\_total, signature\_date\_signed» («Поле 'signature\_date' не найдено. Доступные поля: …») — это помогает Claude исправлять проблемы.

### Зависимости пакетов

Скиллы выполняются в среде исполнения кода с ограничениями, зависящими от платформы:

* **claude.ai:** может устанавливать пакеты из npm и PyPI и скачивать из репозиториев GitHub;
* **Claude API:** нет доступа к сети и установки пакетов во время выполнения.

Перечислите нужные пакеты в SKILL.md и проверьте их доступность по документации [инструмента исполнения кода](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool).

### Среда выполнения

Скиллы работают в среде исполнения кода с доступом к файловой системе, командам bash и возможностью выполнять код. Концептуальное объяснение этой архитектуры — в разделе [Архитектура скиллов](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview#the-skills-architecture) обзора.

**Как это влияет на то, как вы пишете скилл.**

**Как Claude получает доступ к скиллам:**

1. **Метаданные загружаются заранее:** при старте имя и описание из YAML-фронтматтера всех скиллов загружаются в системный промпт.
2. **Файлы читаются по требованию:** Claude через bash и инструменты чтения открывает SKILL.md и другие файлы из файловой системы, когда они нужны.
3. **Скрипты выполняются экономно:** вспомогательные скрипты можно запускать через bash, не загружая их содержимое в контекст. Токены расходует только вывод скрипта.
4. **Большие файлы не штрафуют контекст:** справочные файлы, данные и документация не расходуют токены контекста, пока их не прочитали.

* **Пути к файлам важны:** Claude перемещается по папке скилла как по файловой системе. Используйте прямые слеши (`reference/guide.md`), а не обратные.

* **Давайте файлам говорящие имена:** имена должны отражать содержимое — `form_validation_rules.md`, а не `doc2.md`.

* **Организуйте так, чтобы было легко найти:** структурируйте папки по предметным областям или функциям.

  * Хорошо: `reference/finance.md`, `reference/sales.md`
  * Плохо: `docs/file1.md`, `docs/file2.md`

* **Прикладывайте исчерпывающие ресурсы:** полную документацию API, обширные примеры, большие датасеты — пока к ним не обратились, контекст они не расходуют.

* **Для детерминированных операций предпочитайте скрипты:** напишите `validate_form.py`, а не просите Claude генерировать код проверки.

* **Ясно указывайте намерение:**

  * «Запусти `analyze_form.py`, чтобы извлечь поля» (запуск)
  * «Алгоритм извлечения — в `analyze_form.py`» (чтение как справки)

* **Проверяйте, как Claude обращается к файлам:** убедитесь на реальных запросах, что Claude ориентируется в структуре ваших папок.

**Пример:**

* `bigquery-skill/`

  * `SKILL.md` (обзор, ссылки на справочные файлы)

  * `reference/`

    * `finance.md` (метрики выручки)
    * `sales.md` (данные воронки)
    * `product.md` (аналитика использования)

Когда пользователь спрашивает о выручке, Claude читает SKILL.md, видит ссылку на `reference/finance.md` и через bash читает только этот файл. Файлы sales.md и product.md остаются в файловой системе и не расходуют ни одного токена контекста, пока не понадобятся. Именно эта файловая модель обеспечивает постепенное раскрытие: Claude может перемещаться по файлам и выборочно загружать ровно то, что нужно для каждой задачи.

Полное описание технической архитектуры — в разделе [Как работают скиллы](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview#how-skills-work) обзора.

### Ссылки на инструменты MCP

Если скилл использует инструменты MCP (Model Context Protocol), всегда указывайте полные имена инструментов, чтобы избежать ошибок «tool not found».

**Формат:** `ServerName:tool_name`

**Пример:**

```markdown
Используй инструмент BigQuery:bigquery_schema, чтобы получить схемы таблиц.
Используй инструмент GitHub:create_issue, чтобы создавать задачи.
```

Где:

* `BigQuery` и `GitHub` — имена MCP-серверов;
* `bigquery_schema` и `create_issue` — имена инструментов внутри этих серверов.

Без префикса сервера Claude может не найти инструмент, особенно когда подключено несколько MCP-серверов.

### Не рассчитывайте, что инструменты уже установлены

Не предполагайте, что пакеты доступны:

````markdown
**Плохой пример: предполагает установку**:
«Используй библиотеку pdf, чтобы обработать файл».

**Хороший пример: зависимости названы явно**:
«Установи нужный пакет: `pip install pypdf`

Затем используй его:
```python
from pypdf import PdfReader
reader = PdfReader("file.pdf")
```»
````

## Технические замечания

### Требования к YAML-фронтматтеру

Во фронтматтере SKILL.md обязательны поля `name` и `description` с конкретными правилами проверки:

* `name`: не больше 64 символов, только строчные буквы, цифры и дефисы, без XML-тегов, без зарезервированных слов;
* `description`: не больше 1 024 символов, не пустое, без XML-тегов.

Полное описание структуры — в [обзоре скиллов](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview#skill-structure).

### Бюджет токенов

Держите тело SKILL.md короче 500 строк — так скилл работает лучше всего. Если содержимого больше, разделите его на отдельные файлы по описанным выше шаблонам постепенного раскрытия. Подробности архитектуры — в [обзоре скиллов](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview#how-skills-work).

## Чек-лист эффективного скилла

Прежде чем делиться скиллом, проверьте:

### Базовое качество

* [ ] Описание конкретное и включает ключевые термины
* [ ] В описании есть и что делает скилл, и когда его применять
* [ ] Тело SKILL.md короче 500 строк
* [ ] Дополнительные детали — в отдельных файлах (если нужны)
* [ ] Нет информации, привязанной ко времени (или она в разделе «Устаревшие подходы»)
* [ ] Термины единообразны по всему скиллу
* [ ] Примеры конкретные, а не абстрактные
* [ ] Ссылки на файлы — на один уровень вглубь
* [ ] Постепенное раскрытие применено уместно
* [ ] У порядка работы понятные шаги

### Код и скрипты

* [ ] Скрипты решают проблемы, а не перекладывают их на Claude
* [ ] Обработка ошибок явная и полезная
* [ ] Нет «шаманских констант» (каждое значение обосновано)
* [ ] Нужные пакеты перечислены в инструкциях и проверены на доступность
* [ ] У скриптов понятная документация
* [ ] Нет путей в стиле Windows (везде прямые слеши)
* [ ] Для критичных операций есть шаги проверки
* [ ] Для задач, где важно качество, встроены петли обратной связи

### Тестирование

* [ ] Создано не меньше трёх оценок
* [ ] Проверено на Haiku, Sonnet и Opus
* [ ] Проверено на реальных сценариях использования
* [ ] Учтена обратная связь команды (если применимо)
